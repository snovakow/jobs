HOW IT WORKS
===============================================================================

Three things happen, in order:

  Decide what to aim at.                                                 Once.        Step 1.
  Collect live postings.                                                 Every pass.  Steps 2 and 3.
  Rank them, tell you what to say, remember what you have already seen.  Every pass.  Steps 4 and 5.

Everything else is plumbing for those three.

The plumbing exists because Claude remembers nothing between threads.
Each step writes a plain text file into this repository and the next step
reads it from there. Nothing carries over on its own — not between steps, and
not into a thread already running. That is the whole trick.

Claude Code is home base. Every step but the sweep starts there, as a command typed into a
Claude Code thread of its own, or for Step 5 the one triage ran in. The command reads its prompt from this
file, or for the LinkedIn and Indeed runs from the 02-* file Step 1 built from it, and its inputs from the repository, or from the thread it continues, as /capture and /advice do, and writes any file it produces back
into the repository, where git keeps every version. Two kinds of work happen
outside Claude Code. The sweep runs in Advanced Research on claude.ai, which
Claude Code doesn't have: RUNBOOK.md holds its messages for pasting
there, and you move the file it writes into the repository, where /sweep
checks it. The link check and the LinkedIn and Indeed runs happen in your
own Chrome, which Claude Code drives through the Claude in Chrome extension,
so they browse with your logins and write their files straight into the
repository, and /advice reads the postings it advises on there too.
The link check and the LinkedIn and Indeed runs start their threads in Auto mode, where the extension doesn't ask permission at each new site, as it otherwise does, holding the run until you answer. /advice has no thread of its own to start, since it answers from the triage thread's ranking, so where it asks at each site, that thread switches to Auto mode instead.

Chrome on another computer, signed in to the same Claude account, connects
too, and a browser run then asks which Chrome to use. The names it offers,
Browser 1 and Browser 2, change places from one listing to the next, and
both read as local, so neither says which is the Chrome set up for these
runs, with your LinkedIn log-in. RUNBOOK.md has you choose the confirmation
screen instead: it opens in every connected Chrome, and you click Connect in
the one in front of you.
The sweep's Research run on claude.ai can use Chrome too, for the job boards that render only with JavaScript. Left to itself with two connected, it chose neither and skipped those boards, so the sweep's first message has it switch browsers before it starts, through the same confirmation, while you are there to click Connect.

A pass can also be run from one more Claude Code thread, the one /executioner
starts, which keeps the pass's progress: a pass spans many threads and days,
and you would otherwise keep track of it yourself. It hands each step's
RUNBOOK.md items to the thread they run in, reads the step's result back from
that thread's transcript, so nothing is pasted unless no transcript fits,
confirms the result against the repository with git before the next step goes
out, and says what RUNBOOK.md has next. It runs no step, so each step keeps its own thread, its own setting and its own check.
It also measures each step from its transcript: the model and effort it ran at, its active time, its tokens and the cost Claude Code records for it at API prices. When the steps are done it reviews the pass beside earlier ones and proposes changes to RUNBOOK.md, this playbook, the commands and itself, each with its evidence and the measure that will show whether it worked. It makes only the ones you approve, and they go through /commit like any other change; until then it changes nothing in the repository but its record of the pass. A snag RUNBOOK.md does not cover is recorded too, and only one that nothing later in the pass catches gets a fix before the next step goes out, made the same way.
Its progress is a file of its own under ~/.claude/plans, outside the repository, since it is one pass's progress on this computer. Its record of the pass, run/06-retrospective.txt, is in the repository, since the next pass's executioner starts from it, and Claude Code deletes transcripts, and the files under ~/.claude/plans, 30 days after they last change, by default.
It runs in Auto mode, like the browser steps, so no turn waits on a permission prompt. In Manual mode, its first pass stopped for read-only shell commands its command did not pre-approve, and for edits to its progress file, which Claude Code asked about even though its command then pre-approved them, and each prompt, for a read or an edit within its own scope, held the pass until you came back to it. Plan mode would hold it to the one plan file Claude Code gives each thread, so even its progress would stop for permission. What keeps it to its two files is its instructions: it changes nothing else until you approve a change, and what it changes then is committed only by /commit, after its change check. You enter the command again at each turn, as /executioner Continue, since the command brings its instructions in whole with every turn, so a long pass's summarized context cannot lose them, and gives the turn's effort for its check.
It is not a step: like /commit, its instructions are its command's own.

The resume goes to the steps that make judgements about fit: Step 1, the Step
2 sweep, and Step 4. Steps 3 and 3B don't take it. The LinkedIn and Indeed
runs collect rows off a results page and do no matching.

The resume's skills list weighs every skill the same; its work history does
not. Read as a history, visualization runs through every role, and the
native app and backend skills are there because visualization projects
needed them. Read as a list, it makes general iOS roles and full-stack roles that are really server or cloud infrastructure
look like fits, and visualization looks like one skill among many. So the
three prompts that judge fit each say to read it as a history: Step 1, the
sweep template's READING MY RESUME block, and triage item 2. Native roles
whose product is video, media, 3D or visualization stay in, since the history
covers them, but the native work predates the current Apple stack, so triage
ranks one that asks for current depth in it tier 2 at most.


SIX THINGS TO UNDERSTAND

1. ONE RUN PER COLLECTION STEP, AND ONE CONTINUATION FOR THE SWEEP.
   Step 2 is one Research run covering all four segments, and when its searches run out before its targets do, a second run in the same thread continues it, once, across all four again. Step 3 is one
   browser run through five LinkedIn job descriptions, two for segment 1
   and one for each of the others, and Step 3B is one browser run through
   four Indeed keyword sets, each in two location passes. None comes close
   to the weight of Step 1. Each result row still carries the segment, the
   description, or the set and pass that found it, so the ledger can tell
   which of them are earning their place.

2. RESEARCH FINDS POSTINGS. THE BROWSER CONFIRMS THEM.
   Research searches widely, but a page it reads can be a search index's or
   an aggregator's copy of a posting that closed long ago. It does not
   reliably render job boards built in JavaScript, such as Workday, and it
   cannot get past the anti-bot walls on LinkedIn and Indeed. Claude in
   Chrome loads each page as it stands now. So Step 2B opens every sweep row
   in the browser, on the employer's own site, before triage reads it, and
   LinkedIn and Indeed each get a browser pass of their own, in Steps 3 and 3B.

3. RESEARCH DOES NOT HAND YOU A FILE.
   It returns a report into the thread. After the report lands you send
   one short follow-up in the same thread asking for it to be written to
   a file. That is why each sweep run has two messages instead of one, and a continued sweep sends that follow-up again after the continuation. The
   LinkedIn and Indeed runs take two commands as well, for a different
   reason: the second, /capture, checks the capture before anything is
   written to a file.

4. FILENAMES NEVER CHANGE.
   Every filename in this playbook is fixed. You never edit a date or a
   number into a prompt. A pass writes its result files into run/, named
   identically every time, and every command reads and writes those same
   paths, so there is nothing to attach and no folder to get wrong.

5. THE LEDGER LIVES IN root/ AND NOWHERE ELSE.
   It is the one file that persists and grows. It is never dated, never copied
   into run/, never duplicated. Triage only appends to it, and never rewrites a
   row it did not add this pass. The only other edits are yours: a role you add
   in Step 5, a status there, a tier in its tier check, and the notes a
   RUNBOOK.md fix names. Git keeps every version, so a pass shows up in the
   history as the rows it added.

   Step 1 never writes it once it exists. On a first run it creates
   root/ledger.csv with a header row and nothing else, and Step 1B fails any
   run that touched a ledger already there.

6. EVERY POSTING IS A ROW. PROSE IS NOT A STORAGE PLACE.
   A run that finds something it cannot cleanly accept — outside the date
   window, outside Ontario, a page it could not open — puts it in the table
   with a status token. It does not describe it in a paragraph underneath.
   The closing notes are for patterns, never for postings.

   This rule exists because prose is where the best skills match of a
   thread goes to die. Everything the ledger, the dedupe and the tier
   ranking do downstream keys off rows. A posting that exists only as prose
   is a posting the system cannot see, and it survives exactly one reading.

   The consequence is that a row's presence does not mean "this one
   qualifies". Qualification lives in the location column, as a token.


STATUS TOKENS

Every row in every 03-* and 04-* file begins its location column with one of
these, in caps, followed by an em dash and then the posting's own location
wording, quoted rather than paraphrased. Sweep files use all five; LinkedIn
and Indeed files use the first three, which is what their templates define.

  OK          Meets the location rule as written: Ontario on-site/hybrid, or
              remote with Canadian eligibility explicitly stated.
  RELOCATE    Strong match, wrong place. Names the city and country, and what
              the posting says about work authorization or sponsorship.
  UNCLEAR     Remote, with no stated country eligibility.
  STALE       Matches and still live, but posted outside the 30-day window.
  UNVERIFIED  Read on some other page, or seen only in a search result, but not opened on the employer's own
              site or job board.

There is no sixth token. A row needing two — a stale relocate posting is a
real thing — carries both, space separated, in the order listed above.

RELOCATE exists because you are willing to move for the right opportunity.
In a sweep it carries a higher bar than OK rather than a lower one: a role
has to be worth moving for, not merely one you could hold if you already
lived there. An ordinary match in another country is dropped, not tokened.
If a sweep of six rows or more returns more RELOCATE rows than OK rows, that
bar was ignored; below six rows the ratio is noise. The LinkedIn and Indeed
runs apply no such bar — they do no matching, and token what the posting
states for triage to judge later.

The tokens are defined once, in the appendix templates, and travel from there
into the 02-* prompt files, into the sweep, LinkedIn and Indeed results, into
05-triage.txt, and into the ledger's notes field. A posting that loses its
token somewhere along that chain is how a US-only role comes to look like a
local one three passes later.


MODEL AND EFFORT

Every step has a Recommended setting, a model and an effort level, and some
have a Maximum setting, which over-provisions for when a silent failure
would cost more than the extra usage. Maximum is Fable where the step's work
is open judgement, and Opus at Max effort where the prompt directs the work
explicitly. A step whose Maximum would match its Recommended has only
Recommended. RUNBOOK.md gives each step's settings.

A step's setting is for its main work, and an item that needs less runs
lighter. The sweep's second message only writes out the finished report, so it
goes with Research off, on Sonnet at low effort, and Step 5's bookkeeping in
the triage thread drops to medium effort, while /advice still runs at Max
effort for its own turn. A fix is set by its own work in the same way. In a new
thread, restoring a file from git runs on Sonnet at low effort, since it is one git command, though one that throws work away, and Haiku would save only cents while adding one more model to switch to; editing
the ledger runs on Sonnet, at medium effort for the rows a fix names, or high
where it reads earlier passes' files; and checking a prompt file against its
template runs on Sonnet at high effort, with /verify still judging the file at
Max effort. In the triage thread, which holds what triage decided, a fix
that only adds some of it to the ledger, such as each new row's gap, runs at
medium effort like Step 5's bookkeeping, while a re-rank, or a fix to rows
triage wrote, is triage's own work, at Max effort. RUNBOOK.md names the setting
at each, and gives no reasons: they are here.

The commands fix what a step must not run without. The checks, /verify,
/diffcheck, /capture and changecheck, run on Opus at Max effort, as /commit does, and Setup,
Triage and the advice at Max effort. Two commands fix a light setting instead:
/sweep, whose program counts the sweep's file and whose model reads it for the warning signs a count can't find, for the person to
act on, on Sonnet at medium effort, and /save, whose program reviews and
commits while its model only reports, on Haiku at low effort. Both run in a
fresh context as /verify and /diffcheck do, so a long thread adds nothing
to their cost. The rest comes from the thread, and a command checks it where
it matters: Setup, Triage and the advice stop on any model but Opus or Fable,
and the browser runs stop on any model but Opus, or below xhigh effort. A
command's own setting lasts only for its turn, while a browser run goes on
through Continue and Re-run replies at the thread's, so it checks the
thread's setting rather than fixing its own. That matters because Claude Code
keeps the model and effort last set as the default for new threads, so a
light setting chosen for a fix is still there when the next step starts. A
check at Max effort hands the thread back at the setting it had, and on a
browser run's Maximum setting, already at Max effort, nothing switches midway. /advice reads its postings in Chrome but fixes its own Max effort, so when Chrome fails partway it is run again rather than continued, since a Continue reply would finish the advice at the triage thread's medium effort.

/executioner runs on Opus, at high effort on every turn but three kinds. Its turns route RUNBOOK.md's
items, confirm results against the repository and measure each step, while the judging is the
steps' own and their checks', each at its own setting. The triage review does
more: it reads the ranking for the triage problems RUNBOOK.md names. It runs at xhigh, and so does a turn that looks into a finding that must be settled before the next step goes out.
The retrospective, at the end of the pass, runs at Max effort: it judges the pass and proposes changes to what steers every pass, design work that recurs every pass, which the change check, a check of consistency, does not judge. Making the changes you approve, and fixing what /commit's change check fails, runs at high effort, as a fix thread does, since the change check runs again before anything is committed.
Its effort changes from turn to turn, which a setting fixed in its command could not follow, so it
checks the thread's setting each turn rather than fixing its own: it stops on
any model but Opus, and a turn below the effort its last message named, or
below high at the setup, stops, while one above it proceeds and says so.
Skipping the retrospective only writes its record, so it needs high effort whatever the last message named.

/commit is the last review of a change to what steers every pass: the playbook,
RUNBOOK.md, CLAUDE.md and the commands, often changed at a lower setting than
any step runs at. So it runs on Opus at Max effort, and before it commits, the
changecheck skill reviews what it staged in a fresh context at Max effort, as
/verify checks setup's files: the thread that made a change shares its
blind spots, which is also why RUNBOOK.md has /commit entered in a new
thread. It fixes its own setting, and stops if anything comes before it in its thread, a /model or /effort included, so RUNBOOK.md sets none for it. The person never runs changecheck, so it is hidden from the slash
commands. A FAIL stops the commit until the change is fixed, or until the
person's note with /commit accepts each problem it names. The fix goes to the
thread that made the change, which holds its reasons, or else to a new
one on Opus at high effort: it needs care across the whole system, but not Max
effort, since the change check runs again before anything is committed.


HOW OFTEN

Every step reads everything it needs afresh, so there is no incremental state
to decay. What limits cadence is Indeed's shorter lookback window and posting
lifespan.

The sweep looks back 30 days from the run date, so any cadence inside a month
sees everything it can reach. The LinkedIn search is set to Past month for
the same reason — running it narrower than the sweep buys nothing at any
cadence slower than weekly. Indeed covers 14 days, so a pass more than two
weeks after the last one leaves an Indeed gap. What the sweep reaches is a
limit of its own: a sweep, even continued, gets through only part of its
target companies, and the rest wait for later passes, so the gap between
passes also sets how often each target is checked.

What is at stake beyond that is posting lifespan. Good roles close in roughly
two to three weeks. If the gap between passes is shorter than that, you get at
least one look at everything each pass's sweep reaches. If it is longer, postings open
and close entirely inside the gap — and they do not show up as misses, they
just make the list look thin. You cannot tell a quiet market from a long gap
after the fact. That is why the sweep, its link check and triage alone still
make a real pass, with the LinkedIn and Indeed runs on top when there is time.

A pass rewrites the file of each run it makes, so a 03-* or 04-* file left
from an earlier pass is a run this pass didn't get to. That is a normal
outcome, not a broken pass, and triage tells the two apart with git.

Every command uses these exact paths. Consistency is what makes each step
mechanical instead of a decision.

Only 05-triage.txt, which you read in Step 5, wraps at 79 columns. This
playbook and every other file a step writes are read by the commands' models,
which read a paragraph the same on one line as on ten, so their lines take any
length, and an edit never rewraps a paragraph to fit. The 79-dash rules are not
a width: they mark where each prompt starts and ends, for prompt.py and
review.py.

One file arrives as a download: the sweep's, from claude.ai. You move it
into run/ yourself, replacing run/03-results.txt. /sweep checks it there
against the last pass's sweep and the last pass's file from git, and moves and changes nothing. The
file goes back to claude.ai once, attached to the next pass's sweep, which
starts with what its COVERAGE block says this one did not reach.

The 02-* files are the durable, expensive output: complete standalone prompts
with your target companies, keywords and descriptions baked in. You do not
edit them between passes. The commands read them as they stand.

ledger.csv columns:
  first_seen,status,company,role,source,tier,notes,url
  source is one of: seg1, seg2, seg3, seg4 for the sweep's segments; li1,
    li1b, li2, li3, li4 for the LinkedIn descriptions, li1b being the
    second for segment 1; the Indeed set and pass — in1t, in1r, in2t,
    in2r, in3t, in3r, in4t, in4r, t for Toronto and r for remote; or hand,
    for a row you appended yourself in Step 5. Each run writes it into its
    own first column. If a posting came from more than one, list every
    source, space separated. Recording the specific search is what later
    tells you which searches are earning their place: triage's item 2b
    counts each one's rows against your applications, and Step 1 reworks
    the searches it names.
  tier is one of: 1, 2, 3
  status is one of: new, applied, closed, skipped — defined under
    STATUS VALUES below

FORMAT: every field double-quoted, RFC 4180 style, with one deliberate
departure — line endings are LF, not RFC 4180's CRLF. Role titles and notes
routinely contain commas — "Senior Software Engineer, Graphics" is one field,
and an unquoted ledger corrupts the moment one appears. This is the only file
in the system that isn't pipe-delimited and the only one where a format error
costs you real work.

The line endings matter because git is how you see what a pass did to the
ledger. Triage appends rows, and never rewrites a row it did not add this pass,
so its diff is the rows it added and nothing else, and its reply in the thread confirms
that from git. A CRLF line differs from the committed copy wherever it sits,
and a file converted to CRLF differs on every line at once, which buries the
change you needed to look at. Keep every line LF.

DEDUPE KEY: company plus role title, normalized — never URL alone. The same
role reaches you as a LinkedIn or Indeed URL from Step 3 or 3B and an ATS URL
from Step 2, and URL matching would file those as two separate roles, which
quietly breaks the one thing the ledger exists to do.


STATUS VALUES

Only one distinction here changes the ranking: a row at new or closed goes
back into it when its posting turns up again, and a row at applied or skipped
stays out. Those two differ in what triage counts when it reads your
decisions back against its tiers (item 2b): applied is an application, and
skipped is a role you passed on.

new is the only value Step 4 ever writes. The other three are yours, and each
records something you did or found.

  new       Unresolved. Triage writes it for every row it appends, at every
            tier. You write it on a row you append yourself in Step 5, and
            on a row at closed or skipped that a pass ranks again and you
            leave undecided. It lets a posting back into the ranking, so a
            row sitting at new is not an oversight — it stays there until
            you decide something.

  applied   You submitted. Set it in Step 5 as you send each one, not at the
            end of the thread. This is the single edit the next pass's
            dedupe depends on. It stays applied whatever comes back, a
            rejection included: a pass treats the row the same either way.

  closed    The posting was gone when you went to act on it. Set it when you
            find that, instead of skipped: skipped holds a role out even
            when the employer reposts it, and closed lets it back in.
            Everything that reaches triage is live, so a closed role that
            turns up again has been reposted, and triage ranks it again,
            marked reopened. A row you let sit until its posting closed is
            skipped, not closed.

  skipped   You are not pursuing it. A deliberate pass, whatever the tier:
            a tier 3 you read and agreed with, a tier 1 you decided against,
            a row you let sit past its window without applying. Never written
            by triage — ranking a posting is not a decision to pass on it.

The four are exhaustive. A row is unresolved, you acted, it closed before you
could act, or you ended it. Resist adding outcomes or interview stages: the
ledger exists to stop you re-ranking things you have already handled, not to
run a pipeline. A value earns its place only when a pass does something
different with its rows, and every value added is another hand edit that can
be forgotten.

STEP 1 — SETUP (/setup)
===============================================================================

/setup runs the prompt below, which reads the resume, this playbook and the
last triage's item 2b, searches only for Part A item 3, and writes its files
into root/ over the ones already there. Git keeps the old ones, and git diff
shows exactly what a re-run changed in each prompt. Then it runs Step 1B on
what it wrote. A checks program that comes with the prompt counts each
segment's rows in the sweep's file from each pass, from git, so a re-run reworks
any segment the sweeps left thin over a full round of its targets. A segment short of rows whose round is still open is not thin: the next sweeps start with the companies its list has left, and reworking a list before all of it has been checked would throw out targets nobody tried.

/setup starts only when root/ledger.csv has no uncommitted change. Step 1 has
no use for the ledger, and that is how Step 1B can tell for certain whether
the run touched it.

PART A — analysis. This is a reasoning pass. Search only for item 3, and
only to confirm a careers-page address or whether a company still exists,

STEP 2 — SWEEP (Advanced Research, checked by /sweep)
===============================================================================

The sweep is the one step that runs outside Claude Code, because it needs
Advanced Research. Each of its runs, the first and any continuation, covers all four segments, in the order the
prompt gives them: 1, 3, 2, 4. Segment 1 is where you have the least
competition, and segment 3 is the volume driver.

Research does not hand back a file, so each sweep run takes two messages, both in
RUNBOOK.md: the first runs the search with resume.pdf, 02-sweep.txt and the last pass's 03-results.txt
attached, or with nothing attached for a continuation in the same thread, and the second asks for the report as 03-results.txt. The second goes
with Research off, on Sonnet at low effort: writing out a finished report needs
neither Research nor a stronger model, and a message sent with Research still
on can start another research run. It puts each run's closing notes under a heading line of their own, CLOSING NOTES, RUN 1 for the first run and RUN 2 for a continuation, and the highest run number is how /sweep tells a continued sweep from a single run. It leaves out the last pass's file the first message attached: that file sits in the thread too, and a write-out asked for every row from every run in the thread took its rows and its two sets of closing notes for runs of this one, so a single run looked like three and the last pass's rows came back to be checked again. At low effort the write-out reads its message literally rather than weighing what an attachment is for, so the message names what to leave out instead of leaving it to a higher setting to work out. You move the download into
run/03-results.txt, and /sweep's program checks it against the copy last committed, against the last pass's sweep, and against the last pass's file the first message attached: it refuses a file that is still the copy last committed, isn't the sweep's table, or already ends with a LINK CHECK block, and counts the
rows by segment and by token beside the last pass's, the COVERAGE block, and the signs
below that a count can find. /sweep's model reads the file for the rest. The sweep's file is committed before the link check,
which edits that commit's copy in place, and whose DIFF CHECK compares the
result against it.

The last pass's sweep is its file as committed before its link check, the
last such copy before that pass's triage was committed, so a sweep saved
partway through this pass is never taken for the last one. A sweep from
before 02-sweep.txt last changed ran another prompt, and nothing compares with
it: the count starts again after a prompt change, as triage's SOURCES does.

A sweep run again in the same pass first puts back the last pass's file, as
the last commit that changed 05-triage.txt holds it. The download that failed
has replaced that file in run/, and attached in its place it would start the
new run where the discarded one stopped, sending the last pass's unreached
targets, which the discarded run checked first, to the back of the queue.


WHERE EACH RUN STARTS

Research gives each run a budget of searches, and 02-sweep.txt lists more
target companies and keyword strings than one run's budget covers. A run
works down each segment's lists in order and stops where its searches run
out, so on its own it would check the top of every list each pass and never
the rest. So the run ends its file with a COVERAGE block: for each segment,
the target companies it never reached, the boards it tried and could not
read, and the keyword strings it never searched, with none written out where
there are none, since a missing line reads the same as a run that skipped the
block. The next pass attaches that file, and its WHERE TO START rule has the
run check the companies and strings the block names first, so the lists
rotate and every target is checked within a few passes. The block lists them
in the order the run would have taken them next, its own leftovers ahead of
the top of the list it skipped to reach them: listed in the segment's order
instead, the top of each list would come round again before its end was ever
reached. A target reached this pass waits its turn next pass, and keyword
searches can still find its postings meanwhile. That needs the strings searched at all. Each segment block lists its companies first, and runs that took the list in that order spent their budget on them: one pass's two runs searched 13 of 263 strings, none of segment 3's, though rows from companies off the lists had ranked as well as the listed companies' rows and drawn more applications. So WHERE TO START has a run work the two lists side by side, two companies to each string. A round of the companies takes longer that way, and so does the thin-segment check that waits for a full round. A company listed under more
than one segment takes one visit, which stretches each run's budget further.
After Step 1 reworks a list, the attached file can still name companies it
dropped, and WHERE TO START skips them.

No one sweep reaches a whole list, so a segment's rows are judged over a
round: the latest passes, two at least, that between them reached every
target company in its list, by their COVERAGE blocks. A segment is thin when
every pass of its last full round came back with three rows or fewer. While
no run of latest passes has reached its whole list, its round is open, and a
segment short of rows is only short, not thin.

When /sweep reports target companies not reached after a single run, a
continuation in the same thread spends a second run's budget on them before
the file is saved; RUNBOOK.md has its message. It runs with Research on, at
the step's setting, and once a pass: what is still not reached waits for the
next pass's start. A continuation is a research run, so claude.ai's Research
usage can make it wait, and the LinkedIn and Indeed runs, which don't depend
on the sweep, fill the wait.

A board that would not load is not carried forward. Research cannot render
many job boards built in JavaScript on its own, and one it could not read even with Chrome would fail the same way again, so starting there again would spend the
budget on the same failure. Triage lists those boards for a check by hand
instead. One it skipped only because no Chrome was selected waits its turn like a target reached, and is tried again, with Chrome, when the rotation next reaches it.


WHAT GOOD LOOKS LIKE
Five to fifteen verified postings for each segment. Every row names its
segment and has a URL, a posted date or the word "undated", and a location
column that starts with a status token and then quotes the posting's own
wording rather than paraphrasing it. Most rows are OK; a few carry RELOCATE,
UNCLEAR, STALE or UNVERIFIED. Nothing but patterns and the COVERAGE block sits below the table. A
short list of real postings is the correct outcome, not a failure.

WHAT BAD LOOKS LIKE
Rows with no token. US locations sitting in OK. On a sweep of six rows or more, more RELOCATE rows
than OK rows. Forty rows for one segment. Any of those means the location block
got dropped or summarized when the 02-* file was built — check that file before
re-running. iOS roles on products with no video, 3D or visualization in them,
or full-stack roles that are really server or cloud infrastructure, mean the READING MY RESUME block went the same way,
since it is what rules them out. But a run also lets such a role through on its own, from a file that matches its template, so once the check finds no drift the sweep stands: triage's item 2 ranks the role tier 3, where another sweep would spend a set of Research runs that can slip the same way. A full-stack role whose backend serves what the frontend shows, such as one on a canvas or rendering product, belongs to segment 3 whatever cloud services it names, and is no warning sign at all. A file with no COVERAGE block, or one with
lines missing, leaves the next pass nowhere to start; the thread that wrote the
file can still add it from its report. A posting named in the closing notes with no row above it can mean the EVERYTHING GOES IN THE TABLE block went the same way, but a run also slips into it on its own, from a file that matches its template, naming a posting it dropped or could not open while explaining where a search came up dry. So once the check finds no drift, the sweep stands: triage's item 1c lists those postings as LEADS, where another sweep would spend a set of Research runs that can slip the same way. Rows identical to rows of the last pass's file mean the write-out copied that file in; its rows were triaged last pass, and its notes would pass for this sweep's, so the thread that wrote the file writes it again without them.

"Lots of US rows" is not a tell on its own. Untokened US rows are the tell,
and so is a RELOCATE list longer than the OK list on a sweep of six rows or
more, which means the worth-moving-for bar was ignored. Below six rows the
ratio is noise.


MODEL EFFORT

One run covers four segments, and effort is the lever on how many searches
and page reads it makes, so even Recommended runs at Max effort. A segment short of rows whose round is still open is short of searches, not of reasoning: the continuations and the next passes' starts reach the rest of its list. Move the
sweep to its Maximum setting when a segment comes back thin, with three rows or fewer in every pass of a full round of its targets. That is a reasoning failure, and the stronger model is
what fixes it. All four segments thin at once is the exception: that points at the target lists themselves, and Step 1 is the fix. Segments 2 and 4 come last in the prompt, so they come up short first
if the run runs out of searches, which is why the prompt has it spread its searches
across all four first. A segment still thin on the Maximum setting means
its target list is off — re-run Step 1, which reworks the keywords and
targets of every segment the sweeps left thin.

that has spent its effort in a browser can still reword a row, drop a token or

downstream can see. Its LINK CHECK block says exactly what it meant to change,
so any other difference between its file and the sweep's is a mistake. Finding
one is a diff, the kind of line-by-line reading a person skims halfway down and
a model does not. It runs apart from the thread that edited the file,
and at Max effort for the reason Step 1B does: the way a checker pleases you
is a blanket PASS. The fix for a file that changed more than it was told to
is just as mechanical — the sweep's copy with the block applied — so the check
makes it.

-------------------------------------------------------------------------------
Two copies of run/03-results.txt, a table of job postings with its closing
notes. The research copy is the file a research run wrote, as last committed:
git show HEAD:run/03-results.txt. The checked copy is that file after a check
opened every row's URL in a browser and edited it in place: the file as it
now stands in the working tree. The checked copy ends with a LINK CHECK
block: either the single line LINK CHECK: NONE, or a LINK CHECK: line with
nothing under it but lines of these two kinds:

  CLOSED: [company] | [role title] | [what the page showed] | [URL]
  MOVED: [company] | [role title] | [new URL] | [the title the listing shows]

The check was told to change three things in the research copy and nothing
else: remove the row each CLOSED line names, put the URL each MOVED line gives
in place of its row's own, and add the block as the last thing in the file. A
CLOSED line names its row by company, role title and the row's own URL; a
MOVED line names it by company and role title, and the checked copy shows
which row carries its new URL. The title a MOVED line ends with is the one the listing shows, for triage to read, and changes nothing in the row.

Diff the checked copy against the research copy and account for every
difference. Blank lines around the block do not count; any other difference
does, down to a single character. Print one line for each CLOSED and MOVED
line, giving the row of the research copy it names and whether the checked copy
made that change to that row and no other. Then print one line for each
difference the block does not account for, quoting both copies. Then this line:

  [a] rows in the research copy, [b] in the checked copy, [c] CLOSED lines,
  [d] MOVED lines

and then exactly one of these:

  DIFF CHECK: PASS
  DIFF CHECK: REBUILT — [n] differences the block does not account for
  DIFF CHECK: FAIL — [what kept the check from being made]

FAIL when the check cannot be made: the research copy already ends with a
LINK CHECK block, so the sweep's file is not the last commit; the checked
copy has no block, or one in neither form above; or a CLOSED or MOVED line
names no row of the research copy, or more than one. PASS when every
difference is one the block accounts for. REBUILT otherwise. On PASS or FAIL,
change no file.

On REBUILT, rebuild the checked copy from the research copy. Save the checked
copy outside the repository first. Then restore the research copy from git and
edit it in place rather than retyping it: remove the rows the CLOSED lines
name, put in the URLs the MOVED lines give, then add a blank line and the
block, exactly as the checked copy has it. Diff the rebuilt file against the
research copy the same way and print its counts line; it must leave no
difference the block does not account for.
-------------------------------------------------------------------------------

/linkcheck acts on the verdict:

  PASS      The file is the link check's, ready for triage.
  REBUILT   The check rebuilt the file from the sweep's copy and the block.
            The lines above the verdict say what the link check changed
            besides.
  FAIL      The check could not be made, and its verdict line says why.
            /linkcheck fixes what it names — a missing or malformed block,
            or a line that names no row — in its own thread, which
            still holds every page it opened, then runs the check again. A
            second FAIL stops it: the sweep's committed file is restored and
            the step starts again.

No DIFF CHECK line means the check did not finish, and it runs again. Under a
PASS, the counts line is the evidence: the checked copy holds the research
copy's rows less one per CLOSED line.

CAPTURE CHECK

/capture runs this in the run's own thread, once the run has stopped:

On FAIL, then print this line, with [k] the number of CAPTURE CHECK lines in

  [failed sources and their searches]. Capture only a card whose title

/capture is identical every pass — the searches are already in the
thread and the filename lives in the prompt file, so there is nothing
to give it. The check comes first so that a bad capture is never written to a
file at all: a failed source is held out of the file, and the rest of the
file exists only once its rows have been read against the searches they were
run under. Both outcomes have a fixed line, so a missing CAPTURE CHECK line
means the check was skipped, never that the capture was fine. The file ends
with the same evidence, as a CAPTURE CHECK block: the verdict line, then the
line printed for each row. That block is what lets triage repeat the check from
the file alone (item 1d), and tell a checked file from one the check never
wrote.


WHAT TO EXPECT

Expect this to still be the fiddliest part of the pass. It is a browser
driving a site that does not want to be driven, so a run may lose its place.
That is normal.

How many results a description returns depends on its segment. In testing,
the graphics, video and Apple descriptions each returned less than a page,
so page 1 held every result, while the frontend description returned several
pages, of which the run reads the first. Most of that page is frontend work
without the depth the description asks for, and in testing no rewording
changed that. Ads were few or none.

Partway down, a line says further results "may not be exact matches, but
could still be a great fit". That line is not a cutoff: in testing, the best
fit came after it. When nothing is an exact match, a notice above the first
result says instead that LinkedIn had trouble finding exact matches. The run
reads the whole of page 1 and says in the coverage list where the line fell,
or that the notice appeared.

Results mix Toronto-area and Canada-remote postings, and each card's location
says Remote, Hybrid or On-site. Every Remote result the run captures gets
opened, because that is where US-only and US-work-authorization clauses hide
and the card does not show them. The rest mostly come from their cards, and a
result whose title is plainly unrelated is never opened.

No CAPTURE CHECK line in the thread, or no CAPTURE CHECK block at the
end of the file, means the check did not run in full, and it runs again. The
coverage list would never have told you: it reports what the run believed it
did, and li1 rows full of designers, consultants and backend roles read to the
run as a thin market. Kept, they would put junk rows in the ledger under that
description's source code, polluting the one measurement that tells you which
searches are earning their place. Triage repeats the check on 04-linkedin.txt
(item 1d) from its CAPTURE CHECK block, at Max effort in a thread of its
own. It holds a bad capture out of the ranking and the ledger, and its checks
stop it on a file this pass wrote without the block, so one that gets past
here is still caught — but caught after the run is over, whereas here the run
is still open with the descriptions in front of it.

The check has a limit: it is the thread judging its own capture, and the
judge reads the run's own narration, which frames every row as on-topic. The
evidence lines are the counter — a long-tail row has nothing to quote — and Max
effort is what makes the judgement hold on the subtle case, generic developer
roles under a search for specialist work.

A FAIL still writes the file, keeping every row that a passing source captured
and naming the sources held out, so one bad source costs only the rows no other
source found. The check then prints the re-run message with the failed sources
and their searches filled in, under a line that counts this thread's
FAILs, so nothing is written by hand: a reply of Re-run sends it, as browser
work again at the run's own effort, since /capture's Max effort ended with its
turn. The re-run replaces only the rows those searches alone captured and
reprints everything, then /capture runs again and its file replaces the one
before. Whether to re-run stays the person's call on every FAIL, re-running
while willing to and leaving the gap when not. The count is there because a
rule that keeps failing in one thread is more likely a stale file than
bad luck. A gap left is a gap this pass, so the prompt file is checked against
its appendix template straight away — a rule that did not survive is what a
stale file looks like.

The file must be run/04-linkedin.txt exactly; another name means
02-linkedin.txt has drifted from its template.

This is a step where the more capable model might earn its price: the
whole pass funnels into this single ranking, and the failure the step is
designed around is judgement, not rule-following. On Fable, effort is the
only depth control there is. The prompt was tuned on Opus, so a pass on each
is worth running before settling on Fable. Either way it runs at Max effort,
which /triage sets — this is where a model that wants to please you will
quietly inflate Tier 1 to six roles when the honest answer is two.

Triage writes both files in place, and its reply ends with the CHECKS block.
Its ledger line is the evidence that the ledger gained exactly the rows
triage appended and lost none, so every status you set is still there.
/save's review checks the ledger again, row by row, before anything is
committed: no row lost, and no row's first_seen, company, role, source or url
changed. A status, tier or notes change is a person's edit, so it passes, and
the commit message counts it. /save commits nothing while its review flags
anything: a stray ledger committed would split the history, and a damaged
ledger, once committed, becomes the copy every later check compares against, so
a lost row no longer shows as lost.

Triage names a ledger row by its line in the file, the header counted,
because that is the number an editor shows and the one the ledger checks

would either leave this pass's rows at their old tiers, which the tier check
does not touch, or change rows already committed, which a ledger check run
again counts as changed. A role triage ranked wrong once it is saved is decided
in Step 5 instead.

A Tier 1 of two or three roles is normal and healthy; past passes produced
two to five. A Tier 1 of eight is the model pleasing you, and padding Tier 1
is the specific failure this step is designed around.

On your first ever pass the ledger is empty and dedupe has nothing to compare
against. Expected. It starts paying for itself on the second pass.


===============================================================================
STEP 5 — APPLY
===============================================================================

Each decision is a status in ledger.csv, as STATUS VALUES under FOLDER LAYOUT
defines them. In a row triage wrote, the status is the only field a decision
changes; the one exception is THE TIER CHECK below. Told a decision, Claude
Code sets that row's status and nothing else.

A row that repeats a role already in the ledger, under wording no dedupe check
caught, takes the earlier row's status. The ledger only grows, so the repeat
stays, and the earlier row's status is what was already decided or found about
the role: applied and skipped hold it out, and new leaves it open. Item 2b then
reads that decision twice, a small skew in a rare case, where any other status
would misreport the role. The exception is closed. A closed role that turns up
again was reposted, as STATUS VALUES says, so its repeat is decided on its own,
like a reopened row.


APPLYING

A Tier 1 row comes with triage's advice, in item 3 of 05-triage.txt: the
three resume bullets to lead with, what to cut, and the line to open the
application with. For a row below Tier 1, /advice gets the same advice from
the triage thread, at its own Max effort, reading each posting in Chrome first, since the runs record only a line or two of it. It sends this message with the
roles listed under it:

-------------------------------------------------------------------------------
I'm also applying to the roles listed below, which you ranked below Tier 1.
For each, open its posting at its ledger URL in Chrome and read it, then give me what item 3 gives a Tier 1 role: the three resume bullets
to lead with, what to cut, and the one line the cover letter or application
note should open with, specific to that posting's language. Plain text, no
markdown.
-------------------------------------------------------------------------------

Advice marked unread posting was written without the posting's text. The
LinkedIn and Indeed runs open every remote result but not always the others,
so a role found only as a LinkedIn row whose location does not say Remote, or
as an Indeed Toronto-pass row (in1t, in2t, in3t or in4t), may have been read
from its search card alone. That advice is checked against the posting before
it is used, starting with the one thing triage names to verify.


ANOTHER ROLE WORTH PURSUING

A company strong enough for Tier 1 often has a sibling role no run captured,
on the same board as the posting being applied to, and triage's LEADS list
names more: postings no run opened, and boards worth checking directly. A
role from either that is applied to, or wanted on next pass's list, gets a
row of its own at the end of ledger.csv. Claude Code, given its URL, its
status and a tier, opens the posting — in Chrome, for LinkedIn and Indeed —
and appends the row:

  first_seen  today's date, YYYY-MM-DD
  status      applied if submitted now, new to decide it next pass
  company     exactly as the posting shows it
  role        exactly as the posting shows it
  source      hand
  tier        the tier given: 1, 2 or 3
  notes       the status token its location supports, a semicolon, the
              location wording, a semicolon, then "gap: " and the one thing
              it asks for that the resume lacks: "OK; Toronto ON; gap: no C++"
  url         the posting, on the company's own board where it has one, at
              its own page rather than its application form, with any
              tracking parameters dropped. A LinkedIn or Indeed posting's
              Apply link usually leads to it

Every field double-quoted and LF line endings, as every other row has. The
dedupe key is built from the company and role, so a paraphrased title is how
the same role earns a second row next pass. The url is the employer's own posting where there is one, because a job board's copy can stay up after the role closes. A role ruled out needs no row: it
comes back only if a later run finds it.


THE TIER CHECK

Last, the tiers. Triage's reply in the thread lists every row already in the ledger
that this pass ranked into a different tier, with both tiers. Each takes this
pass's tier, unless it was at applied or skipped before this pass and still
is. No other tier changes, a tier 3 row applied to included. The triage
thread makes the check when asked: it holds the list, and git holds
each row's status from before this pass.

Item 2b is the reason. It reads each decision back against the tier in its
row, so the tier has to be the ranking the decision was made against: this
pass's for a row you decided now or left undecided, and the earlier one for
a decision from an earlier pass that still stands.


THE TIER 3 QUEUE

Triage writes every row as new, tier 3 included, so tier 3 arrives in your
queue rather than filed away behind your back. The five-word reasons make it
quick: two minutes, once a pass, while the postings are still fresh in your
mind.

Do it every pass and the queue stays small. Leave it for three passes and you
are reading two hundred rows cold, which is functionally the same as not
reading them.

Triage could write tier 3 as skipped directly and spare you the pass, and it
would cost more than it saved. skipped would claim a decision nobody had
made, a pile you had never seen and a pile you had read and rejected would
look identical in the file, and the only way to find a good role sitting in
it would be to trip over one. A tier 3 row at new is visibly unreviewed.
That is what the two minutes buys.

The asymmetry is worth naming, because triage is already built to distrust a
Tier 1 of eight — the model pleasing you is a known failure of triage. Tier 3
is that same ranking making the same kind of call. It does not get committed
automatically either.


WHEN A TIER 3 TURNS OUT TO BE WORTH APPLYING TO

Expected, and the reason the queue exists. Apply and set it to applied like
any other row, and leave its tier at 3: that column is triage's output and
the only record of what the ranking said. A row reading tier 3 with status
applied is correct and ought to look odd.

That odd-looking row is the point. Triage reads every decided row back
against its tier each pass (item 2b) and names the kinds of role where your
decisions and its tiers disagree. One override is noise. Three or four of one
kind across consecutive passes means the sweep file or the positioning is
miscalibrated, and the fix is re-running Step 1 rather than reviewing harder.
The exception is a kind whose tier 3 rows you mostly skipped over the same
passes: there the tier matches your choices, and those applications were
reaches.


ROWS THAT SIT

Rows still at new whose first_seen is a couple of months old are not a
maintenance problem to be tidied away. They are the ledger reporting that
triage produced more than you applied to, which is the most useful thing this
file will ever tell you about your own throughput. Read the pile, then either
apply or set them to skipped. Either way it is a decision, and skipped
records it honestly.

  - You finish every set in both passes.
