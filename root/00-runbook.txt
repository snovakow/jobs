HOW IT WORKS
===============================================================================

Three things happen, in order:

  Decide what to aim at.                          Once.        Step 1.
  Collect live postings.                          Every pass.  Steps 2 and 3.
  Rank them, tell you what to say, remember       Every pass.  Steps 4 and 5.
  what you have already seen.

Everything else is plumbing for those three.

The plumbing exists because Claude remembers nothing between conversations.
Each step writes a plain text file and the next step reads it as an
attachment. Nothing carries over on its own — not between steps, and not into
a conversation already running. You attach what a step needs at the moment you
start it, every time. That is the whole trick.

The resume goes to the steps that make judgements about fit: Step 1, the four
Step 2 sweeps, and Step 4. Step 3 doesn't take it. Those runs collect rows off
a results page and do no matching, so the resume would only be one more thing
in front of a browser session that is already the tightest on budget.


SIX THINGS TO UNDERSTAND

1. ONE SEGMENT PER RESEARCH RUN. NEVER MERGE THEM.
   Each Research run has a finite search budget. "Find me graphics, video, XR,
   iOS and frontend roles" spends roughly eight searches per topic and comes
   back shallow on all five. Four separate runs each go deep on one. This is
   why four segment files exist instead of one, and it is the single change
   most likely to look like a simplification and quietly gut the system. Do
   not make it.

   The same applies to Step 3, for a different reason. There the constraint
   is session budget and LinkedIn's tolerance rather than search budget, but
   merging runs fails the same way: it burns everything on the first quarter
   of the work and stalls holding results it never printed. One keyword set,
   one location pass, one conversation.

2. RESEARCH CANNOT READ LINKEDIN OR INDEED.
   They sit behind anti-bot walls. Research does well on company career pages,
   Greenhouse/Lever/Ashby-hosted boards, and aggregators that render server-
   side. LinkedIn is why Step 3 exists as a separate, browser-based pass.

3. RESEARCH DOES NOT HAND YOU A FILE.
   It returns a report into the conversation. After each report lands you send
   one short follow-up in the same conversation asking for it to be written to
   a file. That is why every step here has two messages instead of one.

4. FILENAMES NEVER CHANGE. THE FOLDER CARRIES THE DATE.
   (One exception exists in the whole system: ledger-seed.csv, renamed once
   ever, on your first run. Point 5 explains why.)
   Every filename in this runbook is fixed. You never edit a date or a number
   into a prompt. Each pass gets its own folder, named with the date, and the
   files inside are named identically every time. The only thing you have to
   get right is attaching from the correct folder.

5. THE LEDGER LIVES IN THE ROOT AND NOWHERE ELSE.
   It is the one file that persists and grows. It is never dated, never
   copied into a run folder, never duplicated. Attaching an older copy
   silently destroys your status edits and breaks dedupe.

   Step 1 never writes it. Step 1 writes ledger-seed.csv — a header row and
   nothing else — which you rename to ledger.csv exactly once, on your first
   run, and delete on every run after. The name differs precisely so that a
   re-run cannot replace a year of statuses with an empty file even if you
   save everything it hands you without looking.

6. EVERY POSTING IS A ROW. PROSE IS NOT A STORAGE PLACE.
   A run that finds something it cannot cleanly accept — outside the date
   window, outside Ontario, a page it could not open — puts it in the table
   with a status token. It does not describe it in a paragraph underneath.
   The closing notes are for patterns, never for postings.

   This is here because the first live segment-3 pass buried the single best
   skills match of the session in a sentence below the table. Everything the
   ledger, the dedupe and the tier ranking do downstream keys off rows. A
   posting that exists only as prose is a posting the system cannot see, and
   it survives exactly one reading.

   The consequence is that a row's presence no longer means "this one
   qualifies". Qualification moved into the location column, as a token.


STATUS TOKENS

Every row in every 03-* and 04-* file begins its location column with one of
these, in caps, followed by an em dash and then the posting's own location
wording, quoted rather than paraphrased. Sweep files use all five; LinkedIn
files use the first three, which is what the LinkedIn template defines.

  OK          Meets the location rule as written: Ontario on-site/hybrid, or
              remote with Canadian eligibility explicitly stated.
  RELOCATE    Strong match, wrong place. Names the city and country, and what
              the posting says about work authorization or sponsorship.
  UNCLEAR     Remote, with no stated country eligibility.
  STALE       Matches and still live, but posted outside the 30-day window.
  UNVERIFIED  Corroborated across two or more independent sources, but the
              listing page itself could not be opened.

There is no sixth token. A row needing two — a stale relocate posting is a
real thing — carries both, space separated, in the order listed above.

RELOCATE exists because you are willing to move for the right opportunity.
In a sweep it carries a higher bar than OK rather than a lower one: a role
has to be worth moving for, not merely one you could hold if you already
lived there. An ordinary match in another country is dropped, not tokened.
If a sweep of six rows or more returns more RELOCATE rows than OK rows, that
bar was ignored; below six rows the ratio is noise. A LinkedIn run applies
no such bar — it does no matching, and tokens what the posting states for
triage to judge later.

The tokens are defined once, in the appendix templates, and travel from there
into the 02-* prompt files, into the sweep and LinkedIn results, into
05-triage.txt, and into the ledger's notes field. A posting that loses its
token somewhere along that chain is how a US-only role comes to look like a
local one three passes later.

FORMAT: every field double-quoted, RFC 4180 style. Role titles and notes

in the system that isn't pipe-delimited and the only one where a format error
costs you real work.

THE SEED FILE: Step 1 writes ledger-seed.csv on every run, including
re-runs, because it cannot tell from its attachments which kind of run it is
and guessing wrong in either direction costs you something. On your first run,
rename it to ledger.csv and put it in the root. On every run after, delete the
download. It is deliberately not named ledger.csv so that misfiling it is
harmless.

DEDUPE KEY: company plus role title, normalized — never URL alone. The same
role reaches you as a LinkedIn URL from Step 3 and an ATS URL from Step 2,
and URL matching would file those as two separate roles, which quietly breaks
the one thing the ledger exists to do.


STATUS VALUES

Only one distinction here is mechanical: a row at new re-enters the ranking
next pass, and every other value keeps it out. The other three carry no
machine behaviour at all — they exist so that a suppressed row still says why
it is suppressed.

new is the only value Step 4 ever writes. The other three are yours, and each
records something you did.

  new       Unresolved. Triage writes it for every row it appends, at every
            tier, and you never set it by hand. It is the only value that
            lets a posting back into the ranking, so a row sitting at new is
            not an oversight — it stays there until you decide something.

  applied   You submitted. Outcome still open. Set it in Step 5 as you send
            each one, not at the end of the session. This is the single edit
            the next pass's dedupe depends on.

  rejected  They said no. The only status whose trigger arrives after you
            have stopped looking at the row, which makes it the one most
            likely to go unrecorded. Set it when the reply lands. Silence is
            not a rejection — leave those at applied, where they are already
            suppressed and cost you nothing.

  skipped   You are not pursuing it. A deliberate pass, whatever the tier:
            a tier 3 you read and agreed with, a tier 1 you decided against,
            a row you let sit past its window without applying. Never written
            by triage — ranking a posting is not a decision to pass on it.

The four are exhaustive. A row is unresolved, you acted, they ended it, or
you ended it. Resist adding interview stages: the ledger exists to stop you
re-ranking things you have already handled, not to run a pipeline, and every
value added is another hand edit that can be forgotten.

There is no status for a posting that expired, and none is needed. An expired
posting cannot come back through a sweep, so there is nothing to suppress,
and marking it would overwrite a row whose age is the useful part of it.

THE PASS
===============================================================================

Once Step 1 is done, a pass is the same nine actions every time.

  0. Create a run folder named with today's date.
  1. Sweep segment 3.        -> 03-results-seg3.txt
  2. Sweep segment 1.        -> 03-results-seg1.txt
  3. Sweep segment 2.        -> 03-results-seg2.txt
  4. Sweep segment 4.        -> 03-results-seg4.txt
  5. LinkedIn runs, in this order:
       set 1 toronto, set 1 remote
       set 2 toronto, set 2 remote
       set 4 toronto, set 4 remote
       set 3 toronto, set 3 remote
     Each writes its own 04-linkedin-*.txt. Stop whenever you want.
  6. Triage.                 -> 05-triage.txt, updated ledger.csv
  7. Apply to Tier 1. Set each to applied in the ledger as you go.
  8. Read the Tier 3 reasons and set the ones you agree with to skipped.

The sweeps and the LinkedIn block order themselves opposite ways, and it is
worth being clear that these are two different rules rather than one.

Segments 3 and 1 lead the sweeps because 3 is the volume driver and 1 is
where you have the least competition — if a pass gets cut short, those are
the two that mattered. Nothing is competing for budget here: the four sweeps
are separate conversations with separate search budgets, so sweep order only
protects against you running out of time or quota partway, not against a run
exhausting itself.

Set 3 runs last in the LinkedIn block for a different reason. There the eight
runs really do share your session budget and LinkedIn's patience, so the
narrow sets go first and the broadest one goes last. Set 3 is also the one
whose territory segment 3's sweep already covers well from career pages,
which makes it the cheapest of the eight to lose.

A pass does not have to be one sitting. The sweeps are mostly waiting and can
be spread out. The only rule is that one pass means one folder — do not run
sweeps into one folder and triage out of another.


HOW OFTEN

Every step re-attaches everything, so there is no incremental state to decay.
But the parts of the system have different lookback windows, and one of those
does leave a gap.

The sweeps look back 30 days from the run date, so any cadence inside a month
sees everything they can reach. The Toronto LinkedIn runs are set to Past
month for the same reason — they capture from cards, so running them narrower
than the sweeps buys nothing.

The remote LinkedIn runs stay at Past week. They open every posting and stop
at twenty, so a wider window would not surface more roles, it would only
change which twenty postings spend the budget. That means remote LinkedIn
coverage genuinely lapses once passes are more than a week apart. It is the
one real hole in this system, it is a deliberate trade rather than an
oversight, and the way to close it if you care is to run the four remote
passes on their own weekly cadence between full passes.

What is at stake beyond that is posting lifespan. Good roles close in roughly
two to three weeks. If the gap between passes is shorter than that, you get at
least one look at everything the sweeps cover. If it is longer, postings open
and close entirely inside the gap — and they do not show up as misses, they
just make the list look thin. You cannot tell a quiet market from a long gap
after the fact.

Run it as often as you can. Nothing below breaks if you cannot.

Then read Part A item 4 — the blunt market read. It is the only part of this
system that is about you rather than about postings.


WHAT PART A WILL PROBABLY TELL YOU

Three gaps are visible from the resume before any searching happens. Knowing
them now is what lets you read a thin Tier 1 correctly later, rather than
concluding the market is quiet:

- No C++ anywhere. It is close to table stakes in the rendering and video
  infrastructure postings segments 1 and 2 will surface.
- No Metal, SceneKit, RealityKit, ARKit or visionOS — which is exactly what
  segment 4 is told to emphasize. OpenGL ES2 and Swift are not substitutes
  on an Apple graphics req.
- No testing or CI. Segment 3 is the volume driver and senior frontend
  postings ask for both constantly.

Step 4 item 4 surfaces these again from live postings, which is the version
that tells you whether they are actually load-bearing. This is only so the
first triage doesn't surprise you.


WHEN TO RE-RUN STEP 1

Only when something real changes: a new skill, a shift in what you're aiming
at, an edit to an appendix template, a segment still thin after a bump to
Opus 5 / Max, or two consecutive passes where all four segments come back
thin. Four segments per pass means two passes give you eight observations —
enough to conclude the target list is wrong rather than the market being
quiet.

ONE THING A RE-RUN WILL DESTROY IF YOU LET IT.

The ledger used to be the other one, and no longer is. Step 1 writes
ledger-seed.csv rather than ledger.csv, so a re-run cannot flatten your
history even if you save every file it hands you straight into the root
folder. Delete the seed and carry on. If a run ever hands you a file actually
named ledger.csv, that run ignored its prompt — do not save it.

Your keyword edits. When a LinkedIn keyword turns out too broad, you fix it
by hand in that 02-linkedin-* file. A re-run regenerates all eight from
scratch and will happily reproduce the same bad term, because nothing in the
new conversation knows you replaced it. keyword-edits.txt in the root folder
is what carries those edits across. Attach it to any re-run. When to write a
line and exactly what a line looks like are in KEYWORD-EDITS.TXT at the end
of Step 3, where the edits actually happen.

STEP 2 — SWEEP (Advanced Research, four runs per pass)
===============================================================================

Sonnet 5, Extra effort. A new Advanced Research run per segment — four runs,
one each for segments 3, 1, 2 and 4. Attach resume.pdf and ONE 02-segment-*
file. Never more than one. The entire message is:

Follow its location, recency and verification rules strictly, and use its
output format exactly.
-------------------------------------------------------------------------------

When the report lands, switch to Sonnet 5 / High in the same conversation and

-------------------------------------------------------------------------------
Write that report to a file, verbatim — the full table with every URL and
every status token intact, and the closing notes. Don't re-rank, summarize,

Name the file 03-results-seg1.txt, 03-results-seg2.txt, 03-results-seg3.txt or

Plain text, no markdown: pipe-delimited table, dashed rule under the header,

Glance at the filename it gives back and confirm it matches the segment you

WHAT GOOD LOOKS LIKE
Five to fifteen verified postings. Every row has a URL, a posted date or the
word "undated", and a location column that starts with a status token and
then quotes the posting's own wording rather than paraphrasing it. Most rows
are OK; a few carry RELOCATE, UNCLEAR, STALE or UNVERIFIED. Nothing but
patterns sits below the table. A short list of real postings is the correct
outcome, not a failure.

WHAT BAD LOOKS LIKE
Rows with no token. US locations sitting in OK. A posting named in the
closing notes with no row above it. On a sweep of six rows or more, more
RELOCATE rows than OK rows. Forty rows. Any of those means the location
block got dropped or summarized when the 02-* file was built — check that
file before re-running.

Note that "lots of US rows" stopped being the tell on its own when RELOCATE
arrived. Untokened US rows are the tell now, and so is a RELOCATE list longer
than the OK list on a sweep of six rows or more, which means the
worth-moving-for bar was ignored. Below six rows the ratio is noise.

On your first ever sweep, open two of the URLs by hand. If both are live
postings matching what the table says, trust the rest and stop checking.


MODEL EFFORT

Bump a segment to Opus 5 / Max only when it comes back thin on two
consecutive passes, or when you catch dead links or postings it did not
actually open. That is a reasoning failure, not a search-budget failure.
Don't bump by default — you'd be paying Max effort to read careers pages.
If a bumped segment still comes back thin, the problem is its target list,
not the model — re-run Step 1.


===============================================================================
STEP 3 — LINKEDIN (Claude in Chrome, eight runs per pass)
===============================================================================

Sonnet 5, High effort, logged in to your account. High is the default, so
this usually means leaving it alone — but check it at the top of every run,
since effort is per conversation and this is eight conversations a pass.

Never drop this below High. Lower levels reduce tool calls and trim repeated
output, and in this step tool calls are the work: fewer postings opened
against a cap that already binds, and the running table printed once at the
end instead of after every keyword. EMIT AS YOU GO is what makes this step
recoverable, and repeated output is the first thing a lower setting
economizes on.

Don't bump it above High either. There is no open-ended reasoning here to
reward — this run does no matching, and every judgement it makes is a rule
lookup against the prompt in front of it. What the step needs is a dozen
rules surviving intact across a long agentic loop, which High already gives
you. Above that you are paying for depth the step is designed not to use,
eight times a pass, on browser work that already draws down your plan limit
faster than chat does.

One level for all eight runs, deliberately. The remote pass reads posting
bodies closely and could be argued a step up, but a per-file effort decision
is one more thing to get right eight times, and this system's whole shape is
about removing those.

Nothing is attached to these runs — not the resume, not this runbook. You
paste one prompt file into an empty conversation and that is the entire setup.
Each 02-linkedin-*-*.txt is written to stand alone for exactly that reason.

This is eight separate conversations, not one. Each covers one keyword set in
one location pass — four keywords, nothing else. Open the matching
02-linkedin-*-*.txt, paste it into a fresh side panel conversation, let it
run, then take the file. Then start a new conversation for the next one.

Run them in the order given in THE PASS: sets 1, 2 and 4 in both passes
first, set 3 last.

Then, in the same conversation, once the run has stopped:

-------------------------------------------------------------------------------
Write that table and the coverage list to a file, verbatim, with every URL
intact. Use the filename given at the bottom of the prompt file. Plain text,
no markdown. Give me the download link.
-------------------------------------------------------------------------------

That message is identical for all eight runs — the filename lives in the
prompt file, so there is nothing to edit.


WHY EIGHT RUNS

The first version of this step was one conversation covering all sixteen
keywords across both location passes. It burned most of a session's budget on
a quarter of the work and then stalled, holding rows it had never printed.

Browser work is far more expensive than chat, a stalled session cannot be
asked for its results, and LinkedIn will rate-limit a long run. Eight small
conversations bound all three. It is the same reasoning as ONE SEGMENT PER
RESEARCH RUN — the constraint there is search budget, here it is session
budget and site tolerance, and the fix is the same shape.

Each prompt tells the run to print its running table after every keyword.
That is deliberate and it is what makes the step recoverable: at any moment,
everything captured is already sitting in the conversation as text you can
copy out by hand. Do not ask a run to be tidier about this.


WHAT TO EXPECT

Expect this to still be the fiddliest part of the pass. It is a browser
driving a site that does not want to be driven, so a run may stall, lose its
place, or need nudging. That is normal.

The two passes have different ceilings and different date windows, and both
differences are deliberate.

A Toronto run should be cheap — four searches and at most ten postings
opened. That ten is a soft cap: on a Toronto-filtered search the card already
tells you what you need, so once the cap is reached the run keeps going and
captures from cards. It always finishes its four keywords. Because it is
cheap, it also runs a Past month window, matching the sweeps.

A remote run is the expensive one. Every posting gets opened, because that is
where US-only and US-work-authorization clauses hide and the card does not
show them. Its twenty is a hard stop, because there is no safe fallback — an
unopened posting on that pass is an unchecked posting.

Expect a remote run to stop on the count rather than on running out of
keywords. Twenty opens does not stretch to four keywords unless the set is
very narrow, so in practice a remote run covers its first keyword or two.
That is not a failure and it is not something to fix by raising the cap. It
is why the keywords are ordered narrowest first, and why the window stays at
Past week: the budget is going to decide your coverage either way, so it
should spend itself on the terms where you have the least competition and on
the freshest postings. Note which keywords it missed and either do a top-up
run or let them go.

That is the design expectation, and the first live pass did not meet it: the
four remote runs used 2, 0, 0 and 0 opens of twenty, and every one finished
all four keywords. A remote run that ends on keywords with the cap untouched
is not the budget working. It means the capture rule threw the page away —
look at NO DIVIDER AT ALL, not at the keyword ordering.

Before you move a 04-* file into the run folder, glance down the title column
and ask whether these roles have anything to do with the keywords you just
ran. That is a five-second check and it is the only one that catches a run
capturing below the divider. The coverage list will not tell you — it reports
what the run believed it did. A set 1 file full of designers, consultants and
backend roles is not a thin market, it is a bad capture, and filing it puts
twenty junk rows in the ledger under that run's source code. That pollutes
the one measurement that tells you which keyword sets are earning their
place.

Check the filename while you are there. It must be 04-linkedin-N-toronto.txt
or 04-linkedin-N-remote.txt exactly; a run that strips the hyphens breaks the
attach list at Step 4.

You do not have to do all eight in one sitting, or at all. Six runs and two
gaps is a normal pass. Attach whatever 04-* files exist.


IF A RUN STALLS

Ask for the partial table first, before you try to fix anything. Rows sitting
in the conversation are what you can lose; a stuck page is not. If the
composer is disabled, look for a stop control, then scroll the panel for an
approval prompt sitting below the fold, then check the site tab itself for a
modal or a challenge page.

Because each run prints as it goes, the fallback is cheap: select the last
printed table, paste it into a text editor, save it under that run's
filename. Step 4 only cares about the filename and that the URLs survived.

Note at the bottom of the file which keywords the run never reached. A thin
list reads very differently at triage depending on whether coverage was
complete or cut short.

If LinkedIn starts showing a challenge page, warning you about page volume,
or returning empty searches you can reproduce by hand in another tab, you
have been rate-limited. Retrying makes it worse. Save what you have and come
back to the remaining runs hours later, or drop them.


KEYWORD-EDITS.TXT

Everything about this file belongs here, even though the file itself is
attached to Step 1. Step 3 is where you find out a keyword is bad and Step 3
is where you fix it; Step 1 is only where the record gets read back.

It exists for one reason. A Step 1 re-run rebuilds all eight 02-linkedin-*
files from scratch and cannot see the keywords you replaced by hand, so it
reproduces the same bad term and you rediscover the problem a pass later.
Nothing else in the system reads this file. It is never attached to Steps 2,
3 or 4, and a pass never touches it.

WHEN TO WRITE A LINE. Only when you change a keyword in an 02-linkedin-* file
by hand. That is the entire trigger. Not for a thin run, not for a rate
limit, not for a stalled session, not for a keyword that found nothing.

WHAT MAKES A KEYWORD WORTH REPLACING. Two things.

The first: it returns so many close matches that capping at 25 hands you an
arbitrary slice of an unrelated market. You do not have to judge this
yourself. A run that sees more than about 100 close matches on a keyword
prints a KEYWORD EDIT line after its coverage list naming the term and the
count. That line is the trigger, and it is half of what you record.

Note that this threshold is higher than the 25-cap threshold, on purpose.
Thirty close matches means you captured 25 of 30 and the term is doing its
job. Six hundred means you captured 25 of 600 and the term has stopped
meaning anything.

The second: LinkedIn cannot match the term at all. It answers "No matching
jobs found", or silently substitutes a different term and reports results for
that instead — visionOS became "visions", WebCodecs became "web codecs".
That is not a narrow term working correctly. It is a term the index does not
hold, and it will return nothing every pass forever while occupying one of
four slots. Replace it and record it, or a Step 1 re-run proposes it again.

WHAT IS NOT A REASON TO REPLACE A KEYWORD. Three things that look like
failures and are not:

  - No close matches, where the search actually ran on your term. The term
    is narrow and working correctly and nothing matching was posted in the
    window. This is the expected outcome for the narrowest terms and it is
    why they run first. If LinkedIn substituted the term or returned nothing
    at all, that is the second replacement reason above, not this one.
  - No divider appeared. LinkedIn ignored the term and ranked the general
    market instead. That is a ranking failure on their side, not a fault in
    the term. Replacing it costs you a good keyword and leaves the real
    problem in place.
  - A keyword ate a remote run's whole open budget. Expected — twenty opens
    rarely stretches to four keywords. It only means anything if the close-
    match count was also high, and then the count is what flags it.

WHAT TO WRITE. One line per change, appended to the root copy, in this form:

  set [n] [toronto|remote|both]: replaced "[old term]" with "[new term]",
  returned [count] close matches, [YYYY-MM-DD]

Both halves earn their place. The old term is what stops a re-run
reintroducing it. The count and date are what tell you later whether the
replacement held or whether that slot has been churning for a year.

For a term LinkedIn could not match there is no count, and there may be no
replacement chosen yet. Use this form instead:

  set [n] [toronto|remote|both]: drop "[term]" — LinkedIn returned no
  matching jobs / substituted "[what it searched instead]", [YYYY-MM-DD]

Step 1's own rejections go in the same file, in the same form, with "step 1
rejection" where the count goes. Part B of Step 1 reports any candidate
keyword it rejected under the four keyword tests and what it used instead;
those are the same kind of fact — a term already ruled out — and they stop a
later re-run re-proposing it.

ONE DECISION THIS DOES NOT MAKE FOR YOU. A term that is too broad on the
remote pass may be fine on the Toronto pass, where the pool is far smaller
and the counts are much lower. Patching both keeps the pair's keyword lists
identical, which is what the Step 1 check list expects and what makes "set 1"
mean one thing. Patching only the offending file keeps a keyword that is
still working. Pick one and be consistent; the "both" option in the line
format above exists so the record reads the same either way.

===============================================================================
STEP 5 — APPLY
===============================================================================

Tier 1 only. Use the three lead bullets and the opening line the triage gave
you for each posting.

Apply within a few days of the triage. Anything found at day 25 of its life
has little runway left, and the ranking already accounts for that.

Set each one's status to applied in ledger.csv as you go, not later. If you
skip this, the next pass resurfaces the same roles and re-ranks them, and the
ledger becomes noise.

Roles you consciously pass on go to skipped. That keeps them out of future
rankings without pretending you applied. Anything left at new will correctly
resurface next pass — that is the ledger working, not failing.


CLEAR THE TIER 3 QUEUE

Triage writes every row as new, tier 3 included, so tier 3 arrives in your
queue rather than filed away behind your back. Sort the new rows by tier and
read the tier 3 reasons — five words each, sitting in notes. Set the ones you
agree with to skipped. Two minutes, once a pass, while the postings are still
fresh in your mind.

Do it every pass and the queue stays small. Leave it for three passes and you
are reading two hundred rows cold, which is functionally the same as not
reading them.

An earlier version of this runbook had triage write tier 3 as skipped
directly, to spare you the pass. It cost more than it saved. skipped claimed
a decision nobody had made, so a pile you had never seen and a pile you had
read and rejected looked identical in the file, and the only way to find a
good role sitting in it was to trip over one. A tier 3 row at new is visibly
unreviewed. That is what the two minutes buys.

The asymmetry is worth naming, because WHEN IT GOES WRONG already tells you
to distrust a Tier 1 of eight — the model pleasing you is a known failure of
this step. Tier 3 is that same ranking making the same kind of call. It does
not get committed automatically either.


WHEN A TIER 3 TURNS OUT TO BE WORTH APPLYING TO

Expected, and the reason the queue exists. Apply, then edit that one row:

  status      to applied, when you send it and not before. Setting it early
              suppresses the row while pretending you acted.
  tier        leave it at 3. That column is triage's output and the only
              record of what the ranking said. A row reading tier 3 with
              status applied is correct and ought to look odd.
  notes       after the token and the five-word reason, add the date and one
              line on what triage undervalued.

That notes line is the point. One override is noise. Three or four across
consecutive passes means the segment files or the positioning are
miscalibrated, and the fix is re-running Step 1 rather than reviewing harder.


REJECTIONS

When a rejection arrives, set that row to rejected. It is the only edit in
the system with no pass to prompt it, which is why it is the one that drifts.
Do it from the inbox, the day it lands. Silence is not a rejection; leave
those at applied, where they are already suppressed.


ROWS THAT SIT

Rows still at new whose first_seen is a couple of months old are not a
maintenance problem to be tidied away. They are the ledger reporting that
triage produced more than you applied to, which is the most useful thing this
file will ever tell you about your own throughput. Read the pile, then either
apply or set them to skipped. Either way it is a decision, and skipped
records it honestly.

APPENDIX — PROMPT TEMPLATES AND SEGMENT DEFINITIONS
===============================================================================

You should never need to touch any of this. Step 1 copies these templates into
the 02-* files. They live here so Step 1 has something to copy, and so you can
rebuild an 02-* file by hand if you ever need to.

An edit to a template here changes nothing on its own — it makes the 02-*
files built from it stale. Re-run Step 1, or repatch every affected 02-* file
by hand, before the next pass.

Nothing in this appendix is meant to be pasted as-is — the bracketed lines
are placeholders Step 1 fills in.

Two rules for filling them in. Every word inside a template is verbatim; only
line breaks may move. And a bracket label changes the length of the line it
sits on, so once you drop one, close the paragraph up and rewrap it to 79
columns — a section header must never be left ending on a dangling dash.


SWEEP PROMPT TEMPLATE (source text for Step 1 -> the four 02-segment files)

-------------------------------------------------------------------------------
Find live job postings that fit my background. Resume attached.

SEGMENT (this run only):
[segment description + target companies + keywords — filled in by Step 1]

EVERYTHING GOES IN THE TABLE. Location, recency and verification decide how a
posting is labelled, not whether I get to see it. There is no flagged
section, no eligibility-unclear section, no "worth your own look" paragraph
underneath. If you find yourself about to write a posting into prose because
it doesn't quite fit a rule, it belongs in the table with a status token. Only
the drop rules below remove a posting entirely.

STATUS TOKENS — the location column of every row begins with one of these, in
caps, then an em dash, then the posting's own location wording quoted rather
than paraphrased:

  OK          Meets the location rule below.
  RELOCATE    Strong match, wrong place.
  UNCLEAR     Remote, no stated country eligibility.
  STALE       Matches and still live, posted outside the 30-day window.
  UNVERIFIED  Corroborated across two or more independent sources, listing
              page could not be opened.

There is no sixth token. A row needing two carries both, space separated, in
the order listed above — "RELOCATE STALE".

LOCATION RULES — apply strictly to every posting, then label it.

OK if ONE of these holds:
(a) On-site or hybrid with the work location in Ontario, Canada — Toronto/GTA
    strongly preferred, also Mississauga, Markham, Waterloo-Kitchener,
    Hamilton, Ottawa, London.
(b) Remote, AND the posting explicitly states eligibility for candidates
    located in Canada. This includes "Remote — Canada", "Remote — North
    America", "Remote — US & Canada", or a named Canadian entity/EOR. Company
    HQ location is irrelevant; only stated candidate eligibility counts.

RELOCATE if the posting fails both of those on location alone and is a strong
match on the technical-depth test in the segment block above. I am willing to
relocate for the right opportunity, so these are worth seeing — which means
the bar is higher here than for an OK row, not lower. It has to be worth
moving for, not merely a role I could hold if I already lived there. An
ordinary match that happens to sit in another city is dropped, not tokened.
If you end up with six rows or more and more of them are RELOCATE than OK,
you have set the bar too low; raise it and cut. Below six rows the ratio
means nothing — do not cut a strong posting to balance it.

  "Remote — US only", postings requiring US work authorization, Remote —
  EMEA/LATAM/APAC and anything specifying a time zone that excludes Eastern
  Canada all land here when they are strong, and are dropped when they are
  not.

  Another Canadian city — Vancouver, Montreal, Calgary — is RELOCATE too,
  and the location column must say which city and country, so I can tell a
  domestic move from an international one at a glance.

  For anything outside Canada, put the posting's own words on work
  authorization and sponsorship in the location column: whether it sponsors,
  whether it requires existing authorization, or whether it says nothing. If
  it says nothing, write that. An empty field reads as "not checked".

UNCLEAR if the posting is remote and never states which countries it is open
to. Do not infer eligibility from the company's HQ.

Nothing is rejected for location alone. A posting is dropped only when it
fails the segment's technical-depth test, or fails verification below.
Location decides the token; it never decides the drop.

RECENCY: posted within the last 30 days. Record the posted date exactly as
shown. If no date is visible, write "undated" — do not estimate.

A posting outside the 30-day window that is still live on the employer's own
board gets the STALE token and keeps its real date. Do not drop it and do not
round the date to bring it inside the window. Still-posted-after-60-days is
information — it usually means the role is hard to fill, which is a reason to
show it to me rather than hide it. Drop it only if the posting is actually
gone.

VERIFICATION — this matters more than volume:
- Every posting must have a URL you actually opened and read.
- If a link 404s, redirects to a generic careers page, or the role is closed,
  drop it.
- Do not include any posting recalled from training data.
- Never construct or guess a job URL.
- Fewer verified, well-matched postings beats a long list. If you only find
  six real ones, return six.

There is exactly one exception. A posting you could not open, but which
appears on two or more independent sources with consistent company, title,
location and date, goes in the table with the UNVERIFIED token. Put the
source you actually read in the URL column, and say in the Gap field what you
could not confirm. This covers aggregators that block direct access to
individual listings. It does not cover a posting you inferred, remembered, or
saw once — those are still dropped, and a constructed URL is still never
acceptable.

WHERE TO LOOK: company career pages directly, and ATS-hosted boards
(Greenhouse, Lever, Ashby, Workable, BambooHR, SmartRecruiters, Workday). Also
try Wellfound, Welcome to the Jungle, Built In, and Canadian tech job boards.
Skip LinkedIn and Indeed — you can't read those postings, and I cover them
separately. Check the career pages of the specific companies listed in the
segment block above.

OUTPUT — plain text only, no markdown. One pipe-delimited table, one row per
posting, dashed rule under the header:
Company | Role title | Location + remote eligibility (status token, then the
posting's own wording) | Posted date | Comp if stated | Fit: one sentence
tying it to specific evidence in my resume | Gap: the single biggest thing
I'd be missing or the main risk | URL

One table, and only one. No second table and no sections after it holding
postings — the tokens do that work now.

Sort by fit, strongest first, as a single sequence. Do not group by token: a
strong RELOCATE belongs above a weak OK, and the token is what tells me the
difference.

Then, briefly:
- Any pattern you noticed in what this segment is actually asking for
- The kinds of adjacent role I'd likely have dismissed but shouldn't — the
  postings themselves stay in the table, described here only as a shape
- Where the search came up dry, and why

These closing notes describe patterns. If a specific posting is named in them
and does not also have a row above, the run has made the one mistake this
format exists to prevent.

LINKEDIN PROMPT TEMPLATE (source text for Step 1 -> the eight
02-linkedin-*-*.txt files)

Step 1 produces eight files from this one template: four keyword sets times
two location passes. The bracketed lines are placeholders Step 1 fills in.
Where the template offers a TORONTO and a REMOTE variant, each file gets
exactly one of them — never both, and never a merged version.

-------------------------------------------------------------------------------
I'm on LinkedIn Jobs. This is one of eight small LinkedIn runs, each
covering a single keyword set in a single location pass. This run is:

  SET [n] — [set label]
  [TORONTO PASS | CANADA / REMOTE PASS]

Do not run any other keyword set, and do not run the other location pass, in
this conversation. The other seven runs happen separately. Attempting more
than this in one session is the specific failure this split exists to
prevent.

KEYWORDS — run these searches one at a time, in the order given. That order
is deliberate: narrowest term first. Do not reorder them and do not skip
ahead to one that looks more promising.
  [the four keywords for this set, one per line]

FILTERS — set these once, then leave them alone:
  [TORONTO: Date posted = Past month
            Location = Toronto, Ontario, Canada]
  [REMOTE:  Date posted = Past week
            Location = Canada
            Remote (on-site/remote filter set to remote)]

WHAT TO CAPTURE — LinkedIn job search is semantic, not keyword matching. A
search returns close matches first, then a divider along the lines of "we
found more results that may not be exact matches", then a long tail of
unrelated jobs. Capture only what appears before that divider. If a search
returns no close matches at all, record nothing for that keyword and move on;
do not fall back to the tail.

OVERSIZED CLOSE-MATCH SETS — check the close-match count before you start
capturing a keyword. A broad term can return so many close matches that the
divider stops filtering anything. If a keyword returns more than about 30
close matches, take the first page only (about 25) and say so in the coverage
list at the end, along with the full count.

NO DIVIDER AT ALL — expect this to be the normal case. It does not mean
every result is a close match, and it does not mean there is nothing here.
Do not substitute the total result count for a close-match count, and do not
throw the page away.

Work page 1 card by card instead. Ignore anything marked Promoted — the same
sponsored listings repeat across every search regardless of the term. Read
the remaining titles. Capture a card whose title plainly names this keyword's
subject matter. Open a card whose title is ambiguous but plausibly on-topic,
within this run's open cap, and capture or drop it on what the posting
actually says. Record nothing for the keyword only when no organic card on
page 1 relates to it.

Say in the coverage list that no divider appeared, give the total count, and
name any ambiguous card you decided not to open, with its company, title and
URL. The oversized-set rule above applies only when a divider exists and sits
beyond about 30 results.

[TORONTO: HOW MUCH TO OPEN — take company, title, location wording, posted
date and salary badge from the result card. This is a Toronto-filtered pass,
so a posting whose card shows a Toronto-area location does not need opening in
order to rule out US work authorization. Open the individual posting only when
the location or remote wording on the card is ambiguous, or when no salary
badge is shown. Cap that at 10 opens for the whole run; once you have opened
10, take everything else from cards alone and say so in the coverage list.
This cap does not end the run — finish all four keywords either way.]
[REMOTE: HOW MUCH TO OPEN — take company, title, location wording, posted date
and salary badge from the result card, then open every posting. This is the
pass where US-only and US-work-authorization clauses appear, and the result
card does not reliably show them. Opening postings is the expensive part of
this run, which is why the stop rule below has a hard count on it. Unlike the
Toronto pass you cannot fall back to cards here — an unopened posting on this
pass is an unchecked posting, which is why hitting the count ends the run
rather than downgrading how you capture.]

The section header sits inside each variant above rather than on a line of its
own, so that dropping the label leaves a clean paragraph. Rewrap it after you
do.

EMIT AS YOU GO — this is the most important instruction in this file. After
each keyword, print the running table of everything captured so far in this
conversation, in the output format below. Do not hold rows back to produce
one table at the end. If this session stalls, runs out of budget, or is
interrupted, whatever you have already printed is what survives. Printing the
table four times over the course of this run is expected and is not wasted
effort.

STOP AND REPORT — stop, print the final table and the coverage list, and end
the run when any of these happen:
  - You finish all four keywords.
  [REMOTE only: - You have opened 20 individual postings, even if keywords
    remain.]
  - LinkedIn shows a challenge page, warns you about page volume, or searches
    start returning empty results. That is a rate limit. Do not retry it.
  - You lose track of which keyword or which page you are on.
Do not push through any of them. A partial run I can top up later is useful.
A session that stalls holding unprinted rows is not.

DEDUPE within this run only. The same posting will surface under several of
these four keywords — one row per posting, not one row per keyword. Do not
worry about duplicates against the other seven runs; those are handled at the
triage step.

STATUS TOKEN — begin the location column of every row with one of these,
followed by an em dash and then the posting's own wording:

  OK          Ontario, or remote with Canadian eligibility stated.
  RELOCATE    Stated location is outside Ontario, or outside Canada.
  UNCLEAR     Remote, with no country stated.

Do not skip US-only postings or postings requiring US work authorization.
Capture them as RELOCATE — I am willing to relocate for the right
opportunity.
[TORONTO: RELOCATE will be rare here, since the search is already
location-filtered — it turns up when a card names a non-Ontario location
anyway. Token it and move on. It changes nothing about what you open.]
[REMOTE: Capturing them costs nothing on this pass. You have already spent
the open by the time you learn a posting is US-only, so recording it is free
where discarding it wastes the open. This does not raise the twenty-open cap
and it is not a reason to open more postings.]

This token is a mechanical read of what the posting states. Do not judge
whether a role is worth relocating for — that happens later, with my resume
in hand. This run does no matching.

OUTPUT — plain text, no markdown, no ranking. Two things, in this order,
then a third only if it applies, and nothing else.

First, a pipe-delimited table with a dashed rule under the header row:

company | title | status token + location wording | posted date | salary if
named | URL

Second, a short coverage list: which keywords were capped at 25 and their
full close-match counts, which keywords returned no close matches, which
keywords showed no divider and their total counts, which keywords you did not
reach, whether you hit the open limit, and why the run stopped. If a cap left
close-match cards unopened, name each one with its company, title and URL —
a name without a URL costs me a search to find the posting again. That
coverage list is the only prose I want — no preamble before the table, no
summary after it, no ranking.

KEYWORD EDIT FLAG — a third item, and only when it applies. If a keyword
returned more than about 100 close matches, print one line per such keyword,
exactly in this form:

  KEYWORD EDIT: set [n] [toronto|remote]: replace "[keyword]" — returned
  [count] close matches

If no keyword crossed that threshold, print nothing at all — no line, and no
note saying there was nothing to report.

Flag a keyword for that reason and no other. A keyword that returned no close
matches is narrow and working correctly. A keyword where no divider appeared
is a LinkedIn ranking failure, not a fault in the term. A keyword that used
up the open budget is expected. None of those get flagged. Do not propose a
replacement term either — choosing one is my job, done later against the
whole keyword set.

WRITE THE FILE — when I ask for the file, name it exactly:

  [04-linkedin-[n]-[toronto|remote].txt]

THE FOUR SEGMENTS (source text for Step 1)

SEGMENT 1 — Graphics / XR
  Real-time 3D graphics, WebGL/WebGPU, Three.js, XR/VR/AR, spatial computing,
  game engine and rendering tooling, technical art tooling. Include creative/
  experiential studios and simulation companies.

SEGMENT 2 — Video infrastructure
  Encoding/transcoding pipelines, streaming, codecs, WebRTC, media playback,

SEGMENT 3 — Senior frontend with depth
  Senior/staff frontend and full-stack engineering where the product has real
