HOW IT WORKS
===============================================================================

Three things happen, in order:

  Decide what to aim at.                          Once.        Step 1.
  Collect live postings.                          Every pass.  Steps 2 and 3.
  Rank them, tell you what to say, remember       Every pass.  Steps 4 and 5.
  what you have already seen.

Everything else is plumbing for those three.

The plumbing exists because Claude remembers nothing between conversations.
Each step writes a plain text file and the next step reads it as an
attachment. Nothing carries over on its own — not between steps, and not into
a conversation already running. You attach what a step needs at the moment you
start it, every time. That is the whole trick.

The resume goes to the steps that make judgements about fit: Step 1, the Step
2 sweep, and Step 4. Step 3 doesn't take it. The LinkedIn run collects rows
off a results page and does no matching.

The resume's skills list weighs every skill the same; its work history does
not. Read as a history, visualization runs through every role, and the
native app and backend skills are there because visualization projects
needed them. Read as a list, it makes senior iOS and cloud full-stack roles
look like fits, and visualization looks like one skill among many. So the
three prompts that judge fit each say to read it as a history: Step 1, the
sweep template's READING MY RESUME block, and triage item 2.


SIX THINGS TO UNDERSTAND

1. ONE RUN PER COLLECTION STEP.
   Step 2 is one Research run covering all four segments, and Step 3 is one
   browser run covering every keyword set in both location passes. Neither
   comes close to the weight of Step 1, so splitting them would buy nothing
   and cost a conversation, a prompt file and a results file per piece. Each
   result row still carries the segment, or the set and pass, that found it,
   so the ledger can tell which of them are earning their place.

2. RESEARCH CANNOT READ LINKEDIN OR INDEED.
   They sit behind anti-bot walls. Research does well on company career pages,
   Greenhouse/Lever/Ashby-hosted boards, and aggregators that render server-
   side. LinkedIn is why Step 3 exists as a separate, browser-based pass.

3. RESEARCH DOES NOT HAND YOU A FILE.
   It returns a report into the conversation. After the report lands you send
   one short follow-up in the same conversation asking for it to be written to
   a file. That is why the collection steps — the sweep and the LinkedIn run —
   have two messages instead of one.

4. FILENAMES NEVER CHANGE.
   (One exception exists in the whole system: ledger-seed.csv, renamed once
   ever, on your first run. Point 5 explains why.)
   Every filename in this runbook is fixed. You never edit a date or a number
   into a prompt. A pass writes its result files into a run folder, named
   identically every time. The only thing you have to get right is attaching
   from the correct folder.

5. THE LEDGER LIVES IN THE ROOT AND NOWHERE ELSE.
   It is the one file that persists and grows. It is never dated, never
   copied into a run folder, never duplicated. Attaching an older copy
   silently destroys your status edits and breaks dedupe.

   Step 1 never writes it. Step 1 writes ledger-seed.csv — a header row and
   nothing else — which you rename to ledger.csv exactly once, on your first
   run, and delete on every run after. The name differs precisely so that a
   re-run cannot replace a year of statuses with an empty file even if you
   save everything it hands you without looking.

6. EVERY POSTING IS A ROW. PROSE IS NOT A STORAGE PLACE.
   A run that finds something it cannot cleanly accept — outside the date
   window, outside Ontario, a page it could not open — puts it in the table
   with a status token. It does not describe it in a paragraph underneath.
   The closing notes are for patterns, never for postings.

   This rule exists because prose is where the best skills match of a
   session goes to die. Everything the ledger, the dedupe and the tier
   ranking do downstream keys off rows. A posting that exists only as prose
   is a posting the system cannot see, and it survives exactly one reading.

   The consequence is that a row's presence does not mean "this one
   qualifies". Qualification lives in the location column, as a token.


STATUS TOKENS

Every row in every 03-* and 04-* file begins its location column with one of
these, in caps, followed by an em dash and then the posting's own location
wording, quoted rather than paraphrased. Sweep files use all five; LinkedIn
files use the first three, which is what the LinkedIn template defines.

  OK          Meets the location rule as written: Ontario on-site/hybrid, or
              remote with Canadian eligibility explicitly stated.
  RELOCATE    Strong match, wrong place. Names the city and country, and what
              the posting says about work authorization or sponsorship.
  UNCLEAR     Remote, with no stated country eligibility.
  STALE       Matches and still live, but posted outside the 30-day window.
  UNVERIFIED  Corroborated across two or more independent sources, but the
              listing page itself could not be opened.

There is no sixth token. A row needing two — a stale relocate posting is a
real thing — carries both, space separated, in the order listed above.

RELOCATE exists because you are willing to move for the right opportunity.
In a sweep it carries a higher bar than OK rather than a lower one: a role
has to be worth moving for, not merely one you could hold if you already
lived there. An ordinary match in another country is dropped, not tokened.
If a sweep of six rows or more returns more RELOCATE rows than OK rows, that
bar was ignored; below six rows the ratio is noise. A LinkedIn run applies
no such bar — it does no matching, and tokens what the posting states for
triage to judge later.

The tokens are defined once, in the appendix templates, and travel from there
into the 02-* prompt files, into the sweep and LinkedIn results, into
05-triage.txt, and into the ledger's notes field. A posting that loses its
token somewhere along that chain is how a US-only role comes to look like a
local one three passes later.


MODEL AND EFFORT

Every step names a Recommended setting: a model and an effort level. Some
also name a Max setting, which over-provisions for when a silent failure
would cost more than the extra usage. Max is Fable where the step's work is
open judgement, and Opus at Max effort where the prompt directs the work
explicitly. A step whose Max would match its Recommended lists only
Recommended. On Max, a conversation stays on one setting throughout, and
nothing switches midway.

Ask for these exact filenames. Consistency is what makes attaching mechanical

Your browser drops downloads somewhere else. Move each file into the run

have a stale copy sitting in Downloads — clear it out. Attaching the
wrong pass's file is the most common way this goes wrong, and a
duplicate-numbered download is the earliest warning you get.

The 02-* files are the durable, expensive output: complete standalone prompts
with your target companies and keywords baked in. You do not edit them between
passes. You just attach them.

ledger.csv columns:
  first_seen,status,company,role,source,tier,notes,url
  source is one of: seg1, seg2, seg3, seg4 for the sweep's segments; the
    LinkedIn set and pass — li1t, li1r, li2t, li2r, li3t, li3r, li4t,
    li4r, t for Toronto and r for remote; or hand, for a row you appended
    yourself in Step 5. Both runs write it into their own first column. If
    a posting came from more than one, list every source, space
    separated. Recording the specific set and pass is what later tells
    you which keyword sets are earning their place.
  tier is one of: 1, 2, 3
  status is one of: new, applied, rejected, skipped — defined under
    STATUS VALUES below

FORMAT: every field double-quoted, RFC 4180 style, with one deliberate
departure — line endings are LF, not RFC 4180's CRLF. Role titles and notes
routinely contain commas — "Senior Software Engineer, Graphics" is one field,
and an unquoted ledger corrupts the moment one appears. This is the only file
in the system that isn't pipe-delimited and the only one where a format error
costs you real work.

The line endings matter because this is the one file that is rewritten whole,
every pass, by a model that cannot see the copy it is replacing. Triage returns
the complete ledger rather than a diff, so the only way to check it kept your
history is to compare it against the copy in the root. A file that comes back
CRLF differs from that copy on every line at once, which buries the one line
you needed to look at and defeats the row-count check that sits beside it. Keep
every rewrite LF and a pass shows up as the rows it appended.

THE SEED FILE: Step 1 writes ledger-seed.csv on every run, including
re-runs, because it cannot tell from its attachments which kind of run it is
and guessing wrong in either direction costs you something. On your first run,
rename it to ledger.csv and put it in the root. On every run after, delete the
download. It is deliberately not named ledger.csv so that misfiling it is
harmless.

DEDUPE KEY: company plus role title, normalized — never URL alone. The same
role reaches you as a LinkedIn URL from Step 3 and an ATS URL from Step 2,
and URL matching would file those as two separate roles, which quietly breaks
the one thing the ledger exists to do.


STATUS VALUES

Only one distinction here is mechanical: a row at new re-enters the ranking
next pass, and every other value keeps it out. The other three carry no
machine behaviour at all — they exist so that a suppressed row still says why
it is suppressed.

new is the only value Step 4 ever writes. The other three are yours, and each
records something you did.

  new       Unresolved. Triage writes it for every row it appends, at every
            tier; the only row you ever write it on is one you append
            yourself in Step 5. It is the only value that
            lets a posting back into the ranking, so a row sitting at new is
            not an oversight — it stays there until you decide something.

  applied   You submitted. Outcome still open. Set it in Step 5 as you send
            each one, not at the end of the session. This is the single edit
            the next pass's dedupe depends on.

  rejected  They said no. The only status whose trigger arrives after you
            have stopped looking at the row, which makes it the one most
            likely to go unrecorded. Set it when the reply lands. Silence is
            not a rejection — leave those at applied, where they are already
            suppressed and cost you nothing.

  skipped   You are not pursuing it. A deliberate pass, whatever the tier:
            a tier 3 you read and agreed with, a tier 1 you decided against,
            a row you let sit past its window without applying. Never written
            by triage — ranking a posting is not a decision to pass on it.

The four are exhaustive. A row is unresolved, you acted, they ended it, or
you ended it. Resist adding interview stages: the ledger exists to stop you
re-ranking things you have already handled, not to run a pipeline, and every
value added is another hand edit that can be forgotten.

There is no status for a posting that expired, and none is needed. An expired
posting cannot come back through a sweep, so there is nothing to suppress,
and marking it would overwrite a row whose age is the useful part of it.

THE PASS
===============================================================================

Once Step 1 is done, a pass is the same six actions every time.

  1. Sweep.                  -> 03-results.txt
  2. LinkedIn.               -> 04-linkedin.txt
  3. Triage.                 -> 05-triage.txt, keyword-append-edits.txt,
                                updated ledger.csv
  4. Open keyword-append-edits.txt. NONE: done. Otherwise run Step 4B: it
     patches 02-linkedin.txt and hands you the lines to append to
     keyword-edits.txt.
  5. Apply to Tier 1. Set each to applied in the ledger as you go.
  6. Read the Tier 3 reasons and set the ones you agree with to skipped.

A pass does not have to be one sitting. The sweep is mostly waiting. Triage
attaches what the sweep and the LinkedIn run wrote, from the run folder they
wrote it into.


HOW OFTEN

Every step re-attaches everything, so there is no incremental state to
decay. The lookback windows now all match; what limits cadence is posting
lifespan, covered below.

The sweep looks back 30 days from the run date, so any cadence inside a month
sees everything it can reach. Both LinkedIn passes are set to Past month for
the same reason — running them narrower than the sweep buys nothing at any
cadence slower than weekly.

The remote pass used to stay at Past week, on the theory that the twenty-open
hard stop would bind and the window should keep those opens fresh. The first
real pass finished all four remote sets on two opens of eighty, and the
narrower window meant remote coverage lapsed whenever passes sat more than a
week apart — a real hole paid for by a constraint that never bound. If the
remote pass starts stopping sets on the count instead of the keywords, pass
after pass, the trade has come back. Restore Past week in the remote pass's
FILTERS line, both in 02-linkedin.txt and in the appendix template — an 02-*
edit made without the template edit is silently reverted by a Step 1 re-run.

What is at stake beyond that is posting lifespan. Good roles close in roughly
two to three weeks. If the gap between passes is shorter than that, you get at
least one look at everything the sweep covers. If it is longer, postings open
and close entirely inside the gap — and they do not show up as misses, they
just make the list look thin. You cannot tell a quiet market from a long gap
after the fact.

Run it as often as you can. Nothing below breaks if you cannot. And when a full
pass keeps not happening, shrink it instead of postponing it: the sweep, then a
normal Step 4, is a real pass — two conversations end to end. The LinkedIn run
stacks on top whenever there is time.

      postings triage will cut. The broadest term goes last, where the
      toronto pass will still reach it.

      No bare job titles. LinkedIn's semantic matcher treats a common title
      as relevant to nearly every posting at that level in the city, so a
      title keyword returns hundreds of close matches and the close-match
      divider stops filtering anything. "senior frontend engineer" fails
      this test. "data visualization", "WebXR" and "transcoding" pass it.

      Three further tests. Each one exists because a term that failed it
      burned a slot.

      NO TITLE TOKEN ANYWHERE IN THE STRING, not merely no bare title. The
      matcher latches onto the common word and discards the qualifier, so a
      phrase that happens to contain developer, engineer, manager,
      architect, analyst, designer or lead behaves like the bare title.
      "developer tools" is the trap: it names a product category, it reads
      as a kind of work, and it returns the same inflated close-match set as
      "developer" alone. Reject any string containing one of those words and
      cover the same territory with one that does not — "web performance"

WHEN TO RE-RUN STEP 1

Only when something real changes: a new skill or a materially revised resume,

WHAT TO EXPECT

Expect this to still be the fiddliest part of the pass. It is a browser
driving a site that does not want to be driven, so a run may lose its place.
That is normal.

The two passes have different ceilings, and the difference is deliberate.

The Toronto pass should be cheap — four searches per set and at most ten
postings opened per set. That ten is a soft cap: on a Toronto-filtered search
the card already tells you what you need, so once a set reaches the cap the
run keeps going and captures from cards. It always finishes each set's four
keywords. It runs the same Past month window as everything else.

The remote pass is the expensive one. Every posting gets opened, because that
is where US-only and US-work-authorization clauses hide and the card does not
show them. Each set's twenty is a hard stop for that set, because there is no
safe fallback — an unopened posting on that pass is an unchecked posting.
Reaching it moves the run on to the next set.

Expect a remote set that finds real matches to stop on the count rather than
on running out of keywords. Twenty opens does not stretch to four keywords
unless the set is very narrow. That is not a failure and it is not something
to fix by raising the cap. It is why the keywords are ordered narrowest
first: the cap is going to decide the set's coverage either way, so it should
spend itself on the terms where you have the least competition. Note which
keywords it missed and either do a top-up run or let them go. If cap-stops
become the norm across passes, see HOW OFTEN — the Past week trade has come
back.

The opposite outcome is the one to distrust. A remote set that ends on
keywords with the cap barely touched is not the cap working. It means the
capture rule threw pages away — look at NO DIVIDER AT ALL, not at the
keyword ordering.

A coverage list reporting that page 1 was entirely Promoted, so there was
nothing to evaluate, is that failure in its commonest form and now means one
specific thing: the run was pasted from a stale prompt file. NO DIVIDER AT
ALL judges Promoted cards on their titles like any other card. Repatch
02-linkedin.txt before you rerun it.

Read the verdict as you file. No CAPTURE CHECK line means the message was
skipped: do not file the download — paste the check again. The coverage list
would never have told you: it reports what the run believed it did, and set 1
rows full of designers, consultants and backend roles read to the run as a thin
market. Filed, they would put junk rows in the ledger under that set's source
code, polluting the one measurement that tells you which keyword sets are
earning their place. Triage repeats the check on 04-linkedin.txt (item 1d), at
Max effort in a fresh conversation, and holds a bad capture out of the ranking
and the ledger, so one that gets past here is still caught — but caught after
the run is over, whereas here the run is still logged in with the keyword sets
in front of it.

The check has a limit: it is the conversation judging its own capture, and the
judge reads the run's own narration, which frames every row as on-topic. The
evidence lines are the counter — a long-tail row has nothing to quote — and Max
effort is what makes the judgement hold on the subtle case, generic developer
roles under a technology term. Glance at the evidence lines as you file; it is
faster than reading the raw table against the keywords.

A FAIL still writes the file, holding every source that passed and naming the
ones held out, so one bad set costs only its own rows. The check then hands
back the next message, so that nothing is copied by hand: the re-run message
with the failed sources and their keywords filled in, under a line that counts
this conversation's FAILs and tells you to return to the run's own setting —
browser work again — and paste it. The re-run replaces only the rows captured
under those searches and reprints everything; when it stops, paste the check
again — on Recommended, after switching back to Max — and its file replaces the
one you filed. Whether to paste the re-run is your call, and it stays your call
on every FAIL: the check counts them and hands the message back each time, and
you re-run while you are willing to and leave the gap when you are not. The
count is there because a rule that keeps failing in one conversation is more
likely a stale file than bad luck. A gap you leave is a gap this pass. Check
02-linkedin.txt against the appendix template before the next one — a rule that
did not survive is what a stale file looks like. The evidence lines name any
real rows, which you can lift by URL; a later run surfaces them again with
correct provenance if they are still inside the window.

KEYWORD-EDITS.TXT

Everything about this file belongs here, even though the file itself is
attached to Step 1. Step 3 is where you find out a keyword is bad and Step 3
is where you fix it; Step 1 is only where the record gets read back.

It exists for one reason. A Step 1 re-run rebuilds 02-linkedin.txt from
scratch and cannot see the keywords you replaced by hand, so it
reproduces the same bad term and you rediscover the problem a pass later.
Nothing else in the system reads this file. It is never attached to Steps 2,
3 or 4, and a pass never touches it.

WHEN TO WRITE A LINE. Whenever a keyword changes: Step 4B prints one for every
swap it makes, Step 1 prints one for every rejection (covered below), and you
write one yourself for a swap you make by hand outside a pass. Nothing else:
not a thin run, not a keyword that found nothing.

WHO WRITES IT. Not you, most of the time. 04-linkedin.txt ends in a KEYWORD
EDITS block — NONE, or one KEYWORD EDIT line per flagged keyword — and triage
reads it and writes keyword-append-edits.txt: the lines below, ready to
append, dated, with the set to patch named under each. That
file exists every pass, even when it says NONE, so its absence means triage
skipped the item, never that there was nothing to report. Your part is to
choose any [new term] it left for you — against the four keyword tests in the
Step 1 prompt and against this file, where every recorded term is ruled out —
append its lines here, and make the swaps it names. The forms below are so you
can check its work, and write a line yourself when you swap a keyword outside a
pass.

WHAT MAKES A KEYWORD WORTH REPLACING. Two things, and the run flags both.

The first: it returns so many close matches that capping at 25 hands you an
arbitrary slice of an unrelated market. You do not have to judge this yourself.
A run that sees more than about 100 close matches on a keyword prints a KEYWORD
EDIT line in the KEYWORD EDITS block at the end of its output, naming the term
and the count. That line is the trigger, and it is half of what you record.

Note that this threshold is higher than the 25-cap threshold, on purpose.
Thirty close matches means you captured 25 of 30 and the term is doing its
job. Six hundred means you captured 25 of 600 and the term has stopped
meaning anything.

The second: LinkedIn cannot match the term at all. It answers "No matching
jobs found", or silently substitutes a different term and reports results for
that instead — visionOS became "visions", WebCodecs became "web codecs".
That is not a narrow term working correctly. It is a term the index does not
hold, and it will return nothing every pass forever while occupying one of
four slots. This also prints a KEYWORD EDIT line, in the drop form. Replace
the term and record it, or a Step 1 re-run proposes it again.

WHAT IS NOT A REASON TO REPLACE A KEYWORD. Three things that look like
failures and are not:

  - No close matches, where the search actually ran on your term. The term
    is narrow and working correctly and nothing matching was posted in the
    window. This is the expected outcome for the narrowest terms and it is
    why they run first. If LinkedIn substituted the term or returned nothing
    at all, that is the second replacement reason above, not this one.
  - No divider appeared. LinkedIn ignored the term and ranked the general
    market instead. That is a ranking failure on their side, not a fault in
    the term. Replacing it costs you a good keyword and leaves the real
    problem in place.
  - A keyword ate a remote set's whole open budget. Expected — twenty opens
    rarely stretches to four keywords. It only means anything if the close-
    match count was also high, and then the count is what flags it.

WHAT TO WRITE. One line per change, appended to the root copy, in this form:

  set [n] [toronto|remote|both]: replaced "[old term]" with "[new term]",
  returned [count] close matches, [YYYY-MM-DD]

Both halves earn their place. The old term is what stops a re-run
reintroducing it. The count and date are what tell you later whether the
replacement held or whether that slot has been churning for a year.

For a term LinkedIn could not match there is no count. Use this form
instead, and record the replacement on it too — without that, a Step 1
re-run knows only what to avoid, not what the slot now holds, and picks its
own:

  set [n] [toronto|remote|both]: drop "[term]" — LinkedIn returned no
  matching jobs / substituted "[what it searched instead]", replaced with
  "[new term]", [YYYY-MM-DD]

Step 1's own rejections go in the same file, one line per rejection, in
exactly this form:

  set [n] both: replaced "[old term]" with "[new term]", step 1 rejection,
  [YYYY-MM-DD]

Part B of Step 1 reports any candidate keyword it rejected under the four
keyword tests or for its aim, and what it used instead; those are the same
kind of fact — a term already ruled out — and they stop a later re-run
re-proposing it.

ONE DECISION THIS MAKES FOR YOU. A term that is too broad on the remote pass
may be fine on the Toronto pass, where the pool is far smaller and the counts
are much lower. It gets replaced for both anyway. A set has one keyword list,
which both passes run: that is what "set 1" means. The price is an occasional
Toronto term that was still working; the return is that triage, Step 4B and
the record never have to carry a per-pass case. Every line is marked both.

skip this, the next pass resurfaces the same roles and re-ranks them, and the
ledger becomes noise.

Roles you consciously pass on go to skipped. That keeps them out of future
rankings without pretending you applied. Anything left at new will correctly
resurface next pass — that is the ledger working, not failing.


CLEAR THE TIER 3 QUEUE

Triage writes every row as new, tier 3 included, so tier 3 arrives in your
queue rather than filed away behind your back. Before sorting, set tier on
any row triage reported as re-ranked: the existing row keeps last pass's
number and the sort is on that column. Then sort the new rows by tier and
read the tier 3 reasons — five words each, sitting in notes. Set the ones
you agree with to skipped. Two minutes, once a pass, while the postings are
still fresh in your mind.

Do it every pass and the queue stays small. Leave it for three passes and you
are reading two hundred rows cold, which is functionally the same as not
reading them.

Triage could write tier 3 as skipped directly and spare you the pass, and it
would cost more than it saved. skipped would claim a decision nobody had
made, a pile you had never seen and a pile you had read and rejected would
look identical in the file, and the only way to find a good role sitting in
it would be to trip over one. A tier 3 row at new is visibly unreviewed.
That is what the two minutes buys.

The asymmetry is worth naming, because WHEN IT GOES WRONG already tells you
to distrust a Tier 1 of eight — the model pleasing you is a known failure of
this step. Tier 3 is that same ranking making the same kind of call. It does
not get committed automatically either.


WHEN A TIER 3 TURNS OUT TO BE WORTH APPLYING TO

Expected, and the reason the queue exists. Apply, then edit that one row:

  status      to applied, when you send it and not before. Setting it early
              suppresses the row while pretending you acted.
  tier        leave it at 3. That column is triage's output and the only
              record of what the ranking said. A row reading tier 3 with
              status applied is correct and ought to look odd.
  notes       after the token and the five-word reason, ahead of the gap,
              add the date and one line on what triage undervalued. The gap
              stays last — item 4 reads what follows "gap: " next pass.

That notes line is the point. One override is noise. Three or four across
consecutive passes means the sweep file or the positioning is miscalibrated,
and the fix is re-running Step 1 rather than reviewing harder.


REJECTIONS

When a rejection arrives, set that row to rejected. It is the only edit in
the system with no pass to prompt it, which is why it is the one that drifts.
Do it from the inbox, the day it lands. Silence is not a rejection; leave
those at applied, where they are already suppressed.


ROWS THAT SIT

Rows still at new whose first_seen is a couple of months old are not a
maintenance problem to be tidied away. They are the ledger reporting that
triage produced more than you applied to, which is the most useful thing this
file will ever tell you about your own throughput. Read the pile, then either
apply or set them to skipped. Either way it is a decision, and skipped

  platform. Emphasize apps whose substance is visualization or media —
