HOW IT WORKS
===============================================================================

Three things happen, in order:

  Decide what to aim at.                          Once.        Step 1.
  Collect live postings.                          Every pass.  Steps 2 and 3.
  Rank them, tell you what to say, remember       Every pass.  Steps 4 and 5.
  what you have already seen.

Everything else is plumbing for those three.

The plumbing exists because Claude remembers nothing between conversations.
Each step writes a plain text file and the next step reads it as an
attachment. Nothing carries over on its own — not between steps, and not into
a conversation already running. You attach what a step needs at the moment you
start it, every time. That is the whole trick.

The resume goes to the steps that make judgements about fit: Step 1, the four
Step 2 sweeps, and Step 4. Step 3 doesn't take it. Those runs collect rows off
a results page and do no matching, so the resume would only be one more thing
in front of a browser session that is already the tightest on budget.


FIVE THINGS TO UNDERSTAND

1. ONE SEGMENT PER RESEARCH RUN. NEVER MERGE THEM.
   Each Research run has a finite search budget. "Find me graphics, video, XR,
   iOS and frontend roles" spends roughly eight searches per topic and comes
   back shallow on all five. Four separate runs each go deep on one. This is
   why four segment files exist instead of one, and it is the single change
   most likely to look like a simplification and quietly gut the system. Do
   not make it.

   The same applies to Step 3, for a different reason. There the constraint
   is session budget and LinkedIn's tolerance rather than search budget, but
   merging runs fails the same way: it burns everything on the first quarter
   of the work and stalls holding results it never printed. One keyword set,
   one location pass, one conversation.

2. RESEARCH CANNOT READ LINKEDIN OR INDEED.
   They sit behind anti-bot walls. Research does well on company career pages,
   Greenhouse/Lever/Ashby-hosted boards, and aggregators that render server-
   side. LinkedIn is why Step 3 exists as a separate, browser-based pass.

3. RESEARCH DOES NOT HAND YOU A FILE.
   It returns a report into the conversation. After each report lands you send
   one short follow-up in the same conversation asking for it to be written to
   a file. That is why every step here has two messages instead of one.

4. FILENAMES NEVER CHANGE. THE FOLDER CARRIES THE DATE.
   Every filename in this runbook is fixed. You never edit a date or a number
   into a prompt. Each pass gets its own folder, named with the date, and the
   files inside are named identically every time. The only thing you have to
   get right is attaching from the correct folder.

5. THE LEDGER LIVES IN THE ROOT AND NOWHERE ELSE.
   It is the one file that persists and grows. It is never dated, never
   copied into a run folder, never duplicated. Attaching an older copy
   silently destroys your status edits and breaks dedupe.

  source is one of: seg1, seg2, seg3, seg4 for the sweeps, or the specific

FORMAT: every field double-quoted, RFC 4180 style. Role titles and notes
routinely contain commas — "Senior Software Engineer, Graphics" is one field,
and an unquoted ledger corrupts the moment one appears. This is the only file
in the system that isn't pipe-delimited and the only one where a format error
costs you real work.

DEDUPE KEY: company plus role title, normalized — never URL alone. The same
role reaches you as a LinkedIn URL from Step 3 and an ATS URL from Step 2,
and URL matching would file those as two separate roles, which quietly breaks
the one thing the ledger exists to do.

After you apply to something, change its status to applied. That one edit is
what makes the next pass's dedupe work.


===============================================================================
THE PASS
===============================================================================

Once Step 1 is done, a pass is the same eight actions every time.

  0. Create a run folder named with today's date.
  1. Sweep segment 3.        -> 03-results-seg3.txt
  2. Sweep segment 1.        -> 03-results-seg1.txt
  3. Sweep segment 2.        -> 03-results-seg2.txt
  4. Sweep segment 4.        -> 03-results-seg4.txt
  5. LinkedIn runs, in this order:
       set 1 toronto, set 1 remote
       set 2 toronto, set 2 remote
       set 4 toronto, set 4 remote
       set 3 toronto, set 3 remote
     Each writes its own 04-linkedin-*.txt. Stop whenever you want.
  6. Triage.                 -> 05-triage.txt, updated ledger.csv
  7. Apply to Tier 1. Set each to applied in the ledger as you go.

The sweeps and the LinkedIn block order themselves opposite ways, and it is
worth being clear that these are two different rules rather than one.

Segments 3 and 1 lead the sweeps because 3 is the volume driver and 1 is
where you have the least competition — if a pass gets cut short, those are
the two that mattered. Nothing is competing for budget here: the four sweeps
are separate conversations with separate search budgets, so sweep order only
protects against you running out of time or quota partway, not against a run
exhausting itself.

Set 3 runs last in the LinkedIn block for a different reason. There the eight
runs really do share your session budget and LinkedIn's patience, so the
narrow sets go first and the broadest one goes last. Set 3 is also the one
whose territory segment 3's sweep already covers well from career pages,
which makes it the cheapest of the eight to lose.

A pass does not have to be one sitting. The sweeps are mostly waiting and can
be spread out. The only rule is that one pass means one folder — do not run
sweeps into one folder and triage out of another.


HOW OFTEN

Every step re-attaches everything, so there is no incremental state to decay.
But the parts of the system have different lookback windows, and one of those
does leave a gap.

The sweeps look back 30 days from the run date, so any cadence inside a month
sees everything they can reach. The Toronto LinkedIn runs are set to Past
month for the same reason — they capture from cards, so running them narrower
than the sweeps buys nothing.

The remote LinkedIn runs stay at Past week. They open every posting and stop
at twenty, so a wider window would not surface more roles, it would only
change which twenty postings spend the budget. That means remote LinkedIn
coverage genuinely lapses once passes are more than a week apart. It is the
one real hole in this system, it is a deliberate trade rather than an
oversight, and the way to close it if you care is to run the four remote
passes on their own weekly cadence between full passes.

What is at stake beyond that is posting lifespan. Good roles close in roughly
two to three weeks. If the gap between passes is shorter than that, you get at
least one look at everything the sweeps cover. If it is longer, postings open
and close entirely inside the gap — and they do not show up as misses, they
just make the list look thin. You cannot tell a quiet market from a long gap
after the fact.

Run it as often as you can. Nothing below breaks if you cannot.

WHEN TO RE-RUN STEP 1

Only when something real changes: a new skill, a shift in what you're aiming
at, or two consecutive passes where all four segments come back thin. Four
segments per pass means two passes give you eight observations — enough to
conclude the target list is wrong rather than the market being quiet.

TWO THINGS A RE-RUN WILL DESTROY IF YOU LET IT.

The ledger. Step 1's prompt writes ledger.csv, and on a first run that is
correct — header only. On a re-run it would replace your entire history with
an empty file. The prompt above now guards against this, but check the
returned file list anyway: if a re-run hands you a ledger.csv, do not save it
over the root copy.

Your keyword edits. When a LinkedIn keyword turns out too broad, you fix it
by hand in that 02-linkedin-* file. A re-run regenerates all eight from
scratch and will happily reproduce the same bad term, because nothing in the
new conversation knows you replaced it. Keep a running keyword-edits.txt in
the root folder — one line per change, e.g. "set 3 remote: replaced
<term> with <term>, first returned 200+ close matches" — and attach it to any
re-run.

WHAT GOOD LOOKS LIKE
Five to fifteen verified postings. Every row has a URL, the posting's own
location wording quoted rather than paraphrased, and a posted date or the word
"undated". A short list of real postings is the correct outcome, not a
failure.

WHAT BAD LOOKS LIKE
Forty rows, half of them "Remote — US". That means the location rules got
dropped. Re-run it.

On your first ever sweep, open two of the URLs by hand. If both are live
postings matching what the table says, trust the rest and stop checking.


MODEL EFFORT

Bump a segment to Opus 5 / Max only when it comes back thin on two
consecutive passes, or when you catch dead links or postings it did not
actually open. That is a reasoning failure, not a search-budget failure.
Don't bump by default — you'd be paying Max effort to read careers pages.

STEP 3 — LINKEDIN (Claude in Chrome, eight runs per pass)
===============================================================================

Sonnet 5, logged in to your account. (The Chrome extension has model selection
but no effort setting.)

Nothing is attached to these runs — not the resume, not this runbook. You
paste one prompt file into an empty conversation and that is the entire setup.
Each 02-linkedin-*-*.txt is written to stand alone for exactly that reason.

This is eight separate conversations, not one. Each covers one keyword set in
one location pass — four keywords, nothing else. Open the matching
02-linkedin-*-*.txt, paste it into a fresh side panel conversation, let it
run, then take the file. Then start a new conversation for the next one.

Run them in the order given in THE PASS: sets 1, 2 and 4 in both passes
first, set 3 last.

Then, in the same conversation, once the run has stopped:

-------------------------------------------------------------------------------

intact. Use the filename given at the bottom of the prompt file. Plain text,
no markdown. Give me the download link.
-------------------------------------------------------------------------------

That message is identical for all eight runs — the filename lives in the
prompt file, so there is nothing to edit.


WHY EIGHT RUNS

The first version of this step was one conversation covering all sixteen
keywords across both location passes. It burned most of a session's budget on
a quarter of the work and then stalled, holding rows it had never printed.

Browser work is far more expensive than chat, a stalled session cannot be
asked for its results, and LinkedIn will rate-limit a long run. Eight small
conversations bound all three. It is the same reasoning as ONE SEGMENT PER
RESEARCH RUN — the constraint there is search budget, here it is session
budget and site tolerance, and the fix is the same shape.

Each prompt tells the run to print its running table after every keyword.
That is deliberate and it is what makes the step recoverable: at any moment,
everything captured is already sitting in the conversation as text you can
copy out by hand. Do not ask a run to be tidier about this.


WHAT TO EXPECT

Expect this to still be the fiddliest part of the pass. It is a browser
driving a site that does not want to be driven, so a run may stall, lose its
place, or need nudging. That is normal.

The two passes have different ceilings and different date windows, and both
differences are deliberate.

A Toronto run should be cheap — four searches and at most ten postings
opened. That ten is a soft cap: on a Toronto-filtered search the card already
tells you what you need, so once the cap is reached the run keeps going and
captures from cards. It always finishes its four keywords. Because it is
cheap, it also runs a Past month window, matching the sweeps.

A remote run is the expensive one. Every posting gets opened, because that is
where US-only and US-work-authorization clauses hide and the card does not
show them. Its twenty is a hard stop, because there is no safe fallback — an
unopened posting on that pass is an unchecked posting.

Expect a remote run to stop on the count rather than on running out of
keywords. Twenty opens does not stretch to four keywords unless the set is
very narrow, so in practice a remote run covers its first keyword or two.
That is not a failure and it is not something to fix by raising the cap. It
is why the keywords are ordered narrowest first, and why the window stays at
Past week: the budget is going to decide your coverage either way, so it
should spend itself on the terms where you have the least competition and on
the freshest postings. Note which keywords it missed and either do a top-up
run or let them go.

You do not have to do all eight in one sitting, or at all. Six runs and two
gaps is a normal pass. Attach whatever 04-* files exist.


IF A RUN STALLS

Ask for the partial table first, before you try to fix anything. Rows sitting
in the conversation are what you can lose; a stuck page is not. If the
composer is disabled, look for a stop control, then scroll the panel for an
approval prompt sitting below the fold, then check the site tab itself for a
modal or a challenge page.

Because each run prints as it goes, the fallback is cheap: select the last
printed table, paste it into a text editor, save it under that run's
filename. Step 4 only cares about the filename and that the URLs survived.

Note at the bottom of the file which keywords the run never reached. A thin
list reads very differently at triage depending on whether coverage was
complete or cut short.

If LinkedIn starts showing a challenge page, warning you about page volume,
or returning empty searches you can reproduce by hand in another tab, you
have been rate-limited. Retrying makes it worse. Save what you have and come
back to the remaining runs hours later, or drop them.

===============================================================================
STEP 5 — APPLY
===============================================================================

Tier 1 only. Use the three lead bullets and the opening line the triage gave
you for each posting.

Apply within a few days of the triage. Anything found at day 25 of its life
has little runway left, and the ranking already accounts for that.

Set each one's status to applied in ledger.csv as you go, not later. If you
skip this, the next pass resurfaces the same roles and re-ranks them, and the
ledger becomes noise.

Roles you consciously pass on go to skipped. That keeps them out of future
rankings without pretending you applied. Tier 3 already arrives as skipped,
so the only rows you touch by hand are Tier 1 and Tier 2. Anything left at
new will correctly resurface next pass — that is the ledger working, not
failing.

Once or twice a year, sweep the ledger for rows still at new whose first_seen
is a couple of months old. Those are postings that closed without you
noticing. Set them to closed. Nothing breaks if you don't; they just make the
file harder to read.
