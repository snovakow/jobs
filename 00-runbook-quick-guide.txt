===============================================================================
JOB SEARCH RUNBOOK — QUICK GUIDE

Every prompt, in order, with the minimum needed to run a pass. Nothing here
is new. 00-runbook.txt holds the reasoning, the folder layout, the file
checks and the troubleshooting table; read it when something looks wrong.
===============================================================================


THE PASS

Step 1 runs once, before any of this. After that, a pass is the same nine
actions every time.

  0. Create a run folder named with today's date.
  1. Sweep segment 3.        -> 03-results-seg3.txt
  2. Sweep segment 1.        -> 03-results-seg1.txt
  3. Sweep segment 2.        -> 03-results-seg2.txt
  4. Sweep segment 4.        -> 03-results-seg4.txt
  5. LinkedIn runs, in this order:
       set 1 toronto, set 1 remote
       set 2 toronto, set 2 remote
       set 4 toronto, set 4 remote
       set 3 toronto, set 3 remote
     Each writes its own 04-linkedin-*.txt. Stop whenever you want.
  6. Triage.                 -> 05-triage.txt, updated ledger.csv
  7. Apply to Tier 1. Set each to applied in the ledger as you go.
  8. Read the Tier 3 reasons and set the ones you agree with to skipped.

One pass means one folder — do not run sweeps into one folder and triage out
of another. The ledger stays in the root; everything else a pass writes goes
into the run folder.

STEP 1 — SETUP (chat, run once)
===============================================================================

Opus 5, Max effort. No searching. Attach resume.pdf and 00-runbook.txt. On a
re-run, attach keyword-edits.txt as well if you have one. Never attach
ledger.csv.

Prompt:
-------------------------------------------------------------------------------
Attached: my resume and my job search runbook. Before any searching I want a
positioning read, then the reusable prompt files the runbook describes.

I'm a senior software engineer in Toronto, ~20 years in, with an unusual
concentration: real-time 3D on the web (WebGL/Three.js), WebXR, 360°/
stereoscopic video pipelines, video encoding, WebRTC and real-time
multiplayer, plus Apple platform work. 10+ years at one small company.

The framing I currently use, which I want you to pressure-test rather than
accept: the ten years at Liquid Cinema spanned five distinct products — the
WebGL 360° player, the iOS/tvOS clients, WebXR support, WebRTC multi-user
video, and the collaborative metaverse platform — so it reads as range, not
maintenance. I lead with the Meta Quest collaboration, the three 2021 WebXR
Poly Awards, and the Fraunhofer HHI OMAF integration as external validation.

PART A — analysis. Don't search; this is a reasoning pass.

1. Title taxonomy — every job title actually used in postings that maps to
   this background, grouped by how well it fits. Include titles I'd probably
   filter past (e.g. "Creative Technologist", "Media Systems Engineer") if
   the underlying work matches.

2. Keyword sets — the literal strings to type into a board search for each
   cluster, including frameworks and standards (WebXR, OMAF, glTF, WebGPU,
   WebCodecs, etc.).

3. Target companies for Ontario + Canada-remote, organized by cluster:
   XR/spatial computing; game and engine tooling; video infrastructure and
   streaming; medical/scientific visualization; digital agencies and
   experiential studios; simulation and digital twin; mapping/geospatial.
   Real companies with a Canadian presence or known Canada-remote hiring.

   Describe each company, never gate it. No entry may say a company counts
   only if the posting is remote, or only if it sits in Ontario. The segment
   file's own location rules decide that per posting, and an entry that
   pre-filters on location makes the run drop postings those rules say to
   keep and token.

   You are working from memory here with no search, and this list gets baked
   into files I reuse for months — so be conservative. Give a careers-page
   URL only where you are confident of the exact address; write "careers URL
   unknown" otherwise. A guessed URL is worse than none, because a later run
   treats it as a real place to look and spends budget there. Flag any
   company you are unsure still exists, still hires in Canada, or may have
   been acquired.

4. A blunt read on my market position: where ten years at one small company
   helps and where it hurts, where my stack is dated against current
   expectations, what a hiring manager would probe, which clusters I'm a
   strong fit for and which are a stretch, and whether the framing above
   actually holds up.

PART B — write these files and give me download links:

  01-positioning.txt
      All of Part A, in full.

  02-segment-1-graphics-xr.txt
  02-segment-2-video-infra.txt
  02-segment-3-frontend-depth.txt
  02-segment-4-apple-platforms.txt
      One per segment. Each must be a COMPLETE, STANDALONE prompt I can hand
      to Advanced Research with nothing attached but my resume. Take the
      template in the runbook's appendix verbatim — the everything-goes-in-
      the-table rule, the status tokens, location rules, recency rule,
      verification rules, where-to-look list and output format all stay
      exactly as written — and fill in its SEGMENT block from the runbook's
      definition of that segment, including its technical-depth test line,
      plus, from your Part A work, the most relevant target companies for
      that cluster with careers URLs where you have them, and the literal
      keyword strings for that cluster. Assume the reader has never seen the
      runbook or this conversation. Leave no placeholder brackets.

  02-linkedin-1-toronto.txt
  02-linkedin-1-remote.txt
  02-linkedin-2-toronto.txt
  02-linkedin-2-remote.txt
  02-linkedin-3-toronto.txt
  02-linkedin-3-remote.txt
  02-linkedin-4-toronto.txt
  02-linkedin-4-remote.txt
      Eight standalone Claude-in-Chrome prompts, built from the LinkedIn
      prompt template in the runbook's appendix. Four keyword sets, each in
      two location passes. Each file is one complete prompt covering exactly
      one set in exactly one pass — no file may carry another set's keywords
      or the other pass's filters, caps or stop rules; the template's own
      warning against running other sets stays, as part of the prompt. Fill
      in the set number, the set label, the four keywords, the location
      filter, the open-postings block and the stop rules from the template's
      toronto/remote variants, the set and pass in the KEYWORD EDIT FLAG
      line, and the output filename at the bottom. Leave no placeholder
      brackets and no stranded section headers, except [keyword] and [count]
      in that same KEYWORD EDIT FLAG line, which the run fills in when it
      prints.

      Set n covers the same territory as segment n: set 1 graphics/XR, set 2
      video infrastructure, set 3 frontend with depth, set 4 Apple
      platforms. The run ordering in the runbook depends on that
      correspondence, so do not reorganize the sets on some other axis.

      Four sets, exactly four keywords each. LinkedIn job search is
      semantic rather than keyword matching, so near-synonyms return heavily
      overlapping results and a long list buys nothing — within each set
      pick the four terms most different from one another.

      ORDER THE KEYWORDS NARROWEST FIRST within each set, and use the same
      order in that set's toronto and remote file. The remote runs open every
      posting and hard-stop at twenty, so in practice they get through the
      first keyword or two and no further — whichever term you put first is
      the one that actually runs. Narrow, low-competition terms go first. The
      broadest term goes last, where the toronto pass will still reach it.

      Every keyword must name a technology, a standard, or a kind of work.
      No bare job titles. LinkedIn's semantic matcher treats a common title
      as relevant to nearly every posting at that level in the city, so a
      title keyword returns hundreds of close matches and the close-match
      divider stops filtering anything. "senior frontend engineer" fails
      this test. "data visualization", "WebXR" and "transcoding" pass it.

      Three further tests. Each one exists because a term that failed it
      burned a slot.

      NO TITLE TOKEN ANYWHERE IN THE STRING, not merely no bare title. The
      matcher latches onto the common word and discards the qualifier, so a
      phrase that happens to contain developer, engineer, manager,
      architect, analyst, designer or lead behaves like the bare title.
      "developer tools" is the trap: it names a product category, it reads
      as a kind of work, and it returns the same inflated close-match set as
      "developer" alone. Reject any string containing one of those words and
      cover the same territory with one that does not — "web performance"
      in place of "developer tools".

      NO ORDINARY ENGLISH WORD WITH A LARGE NON-TECHNICAL JOB MARKET. Some
      technology names are also common nouns and semantic matching cannot
      tell which sense you meant. "Metal" returns fabrication and
      manufacturing postings and is unusable as the Apple graphics API;
      "Rust", "Go", "Unity", "Processing" and "Spark" have the same problem
      to varying degrees. Pick an unambiguous neighbour — SwiftUI rather
      than Metal.

      THE INDEX HAS TO HOLD THE TERM. Precision can go too far. A framework
      or platform name with a very small posting footprint makes LinkedIn
      answer "No matching jobs found", or quietly search something else —
      visionOS became "visions", WebCodecs became "web codecs". A term like
      that is not narrow and working correctly; it returns nothing every
      pass while occupying one of four slots. Prefer the nearest term you
      would expect to appear in the body of many real postings, and check
      keyword-edits.txt for terms already ruled out this way.

      If keyword-edits.txt is attached, honour all of it: every term it
      records as replaced, dropped or rejected is ruled out whatever test
      it failed, and its recorded replacements stay unless one fails a test
      above.

  ledger-seed.csv
      Write this every run, including re-runs. Do not try to work out
      whether this is my first run — you cannot see my root folder, and
      both ways of guessing wrong cost me something. The filename is
      ledger-seed.csv and never ledger.csv, so that it cannot overwrite the
      live ledger holding every status I have set across every pass. I
      rename it once on a first run and delete it every time after.

      Header row only, fields double-quoted:
      "first_seen","status","company","role","source","tier","notes","url"

FORMAT — plain text, no markdown anywhere: no #, no **, no markdown tables.
ALL-CAPS headers, dashed rules, tables pipe-delimited with a dashed rule under
the header row. Wrap at 79 columns.

Where dropping a bracket label out of a template leaves a section header
stranded, close the paragraph up and rewrap it. No header may end on a
dangling dash, and no line may run past 79 columns because a label used to sit
on it. Only line breaks may move — never a word.

In chat give me Part A in full. For Part B just list the files created, plus
any candidate keyword you rejected under the four keyword tests and what you
put in its place. That is what I copy into keyword-edits.txt, one line per
rejection.
-------------------------------------------------------------------------------

Check the fourteen files against CHECK THE FILES BEFORE YOU USE THEM in the
runbook. If any fail, say so in that same chat and ask for the file again.

Move the 02-* files and 01-positioning.txt into the root folder, replacing
the old ones. Append any reported keyword rejections to keyword-edits.txt.
ledger-seed.csv: first run, rename it to ledger.csv and move it to the root;
any run after, delete it.

Order: set 1 toronto, set 1 remote, set 2 toronto, set 2 remote, set 4

===============================================================================
STEP 4 — TRIAGE (chat, one run per pass)
===============================================================================

Opus 5, Max effort.

Attach from the run folder: every 03-results-seg*.txt and 04-linkedin-*.txt
that exists. From the root: resume.pdf and ledger.csv, and optionally
01-positioning.txt — the only one to drop if fifteen attachments won't fit.
Say in the message which runs are missing. Check twice that ledger.csv is
the root copy.

Prompt:
-------------------------------------------------------------------------------
Attached: my resume, this pass's raw job search results (the 03-* and 04-*
files), and ledger.csv — my running record of everything surfaced previously.
On a first pass it holds a header row and nothing else; that is expected and
not a sign anything was lost. If 01-positioning.txt is attached as well, use
it as background for items 4 and 5.

1. Dedupe across all the attached result files. Match on company plus role
   title, normalized — not on URL. The same role reaches me as a LinkedIn
   URL from one file and an ATS URL from another, and URL matching would
   file those as two separate roles. Where a role has two URLs, keep the one
   closest to the employer's own application page. Flag any that are
   staffing-agency reposts of the same underlying role.

   Normalized means case-folded, with dashes and slashes read as spaces,
   punctuation and repeated spaces collapsed, and any trailing location or
   remote suffix dropped — "Senior Web & Video Player Engineer - Remote" and
   "Senior Web & Video Player Engineer" are one role. Put the normalized
   title in the ledger's role field and the posting's own wording in notes.
   Use this same rule every pass: normalizing differently than last pass
   stops the ledger matching, silently.

   Then check each remaining posting against the ledger, by that same key:
   anything already there with status applied, rejected or skipped goes in a
   short "already seen" list rather than the main ranking — unless the
   posting itself has materially changed (new level, new location wording,
   reposted with a new date), in which case rank it and say what changed.
   Anything already there at status new goes back into the ranking, marked
   as already in the ledger. Either way, a posting already in the ledger
   under that key — at any status — never gets a second row: appending is
   only for postings not in the ledger at all, and the existing row stays
   untouched.

1b. Every row in the attached files begins its location column with a status
   token: OK, RELOCATE, UNCLEAR, STALE or UNVERIFIED. Carry that token
   through everything you write. It appears in the tier list you give me in
   chat, in 05-triage.txt, and at the front of the ledger's notes field. A
   role must never lose its token between the sweep and the ledger — that is
   how a US-only posting comes to look like a local one three passes later.
   If a row arrives with no token, work out which one it should carry from
   its location wording and say that you did.

   Rank tokened rows in the same three tiers as everything else, on fit. Do
   not quarantine them in a list at the end and do not discount a role for
   its token alone. Two constraints on that:

   - "Tier 1 is thin", which is what Step 5 acts on, counts OK rows only. A
     Tier 1 of one OK role and four RELOCATE roles is a thin Tier 1, and I
     want you to say so in those words rather than reporting five.
   - Every RELOCATE row in Tier 1 or 2 gets one line on what the move
     actually involves: which city and country, and what the posting says
     about work authorization or sponsorship. Every UNCLEAR or UNVERIFIED
     row in Tier 1 or 2 gets one line on the single thing I'd need to
     confirm before applying, and whether it's worth the email.

2. Rank everything in the main ranking into three tiers:
   TIER 1 — apply now. Strong fit, real chance, worth tailoring for.
   TIER 2 — apply if Tier 1 is thin. Partial fit or a long shot.
   TIER 3 — skip, and say in five words why. That reason goes into the
   ledger's notes field, where it is the only thing I will have to
   review the row by later.

   For Tier 1 and 2, tell me if I'd be under-levelled, over-levelled, or
   right. Where two roles are otherwise comparable, rank the more recently
   posted one higher — it has more runway before it closes. Don't inflate
   Tier 1 to make the list look healthy — if only two roles belong there, say
   two.

3. For each Tier 1 role: which three resume bullets to lead with, what to
   cut, and the one line the cover letter or application note should open
   with. Be specific to that posting's language.

4. Across the whole set: what skill or credential keeps appearing that I
   don't have? If I could plausibly close it in a few weekends, say so. If
   it's not closeable, say that instead.

5. Sanity-check my standard framing against the actual language in these
   postings — the Liquid Cinema decade as five distinct products rather than
   ten years of maintenance, and leading with the Meta Quest collaboration,
   the three 2021 WebXR Poly Awards, and the Fraunhofer HHI OMAF integration.
   Tell me where that emphasis should shift for this pass's Tier 1 roles.

WRITE THESE FILES and give me download links:

  05-triage.txt
      All of items 1-5 in full. No date in the filename. Plain text, no
      markdown — ALL-CAPS headers, dashed rules, pipe-delimited tables,
      wrapped at 79 columns.

  ledger.csv
      The attached ledger, updated. Keep every existing row completely
      unchanged — every field, not just status. Append one row per posting
      not already in the ledger under the dedupe key; a posting already
      present, at any status, never gets a second row. For each appended
      row:

        first_seen  today's date, YYYY-MM-DD
        source      seg1, seg2, seg3 or seg4 for the sweep files; for
                    LinkedIn, the specific run it came from — li1t, li1r,
                    li2t, li2r, li3t, li3r, li4t, li4r. If a posting
                    appeared in more than one file, list every source,
                    space separated.
        tier        your ranking: 1, 2 or 3.
        status      new. Every row, every tier, without exception. new is
                    the only value you write. applied, rejected and skipped
                    record decisions I have made, and ranking a posting is
                    not one of them. In particular do not write skipped for
                    tier 3 — that reads as my decision to pass, and I make
                    that call myself after reading your reason.
        notes       begins with the posting's status token (both, space
                    separated, when a row carries two), then a semicolon,
                    then the posting's location wording, then a semicolon,
                    then whatever else belongs there. For RELOCATE the
                    location wording must name the city and country:
                    "RELOCATE; Los Angeles US; no sponsorship stated". The
                    token is not a column and must never be promoted to
                    one.

                    For every tier 3 row, item 2's five-word reason goes in
                    directly after the location wording's semicolon:
                    "OK; Toronto ON; mostly CRUD, no graphics". The ledger
                    is the only place that reason survives — 05-triage.txt
                    goes into a dated run folder and is not opened again —
                    and it is what I read when I clear the tier 3 queue.

      Same columns, same order, every field double-quoted RFC 4180 style —
      role titles contain commas. Return the complete file, not a diff.

In chat, give me item 2's tier list and item 4 — that's what I act on. The
rest I'll read in the file.

Move 05-triage.txt into the run folder. Save the updated ledger.csv over the
root copy. Do not keep both.


===============================================================================
STEP 5 — APPLY
===============================================================================

Tier 1 only, within a few days, using the triage's three lead bullets and
opening line. Set each one to applied in ledger.csv as you send it, not
later.

Then clear the tier 3 queue: read the five-word reasons in notes and set the
ones you agree with to skipped. If one is worth applying to: apply, set it
to applied, leave tier at 3, and add the date and what triage undervalued to
notes.

When a rejection arrives, set that row to rejected the day it lands. Silence
is not a rejection — leave those at applied.

The four statuses, for when you are editing the file:

  new         triage wrote it; nothing decided yet — re-enters next ranking
  applied     you sent it
  rejected    they said no
  skipped     you passed
