THE PASS

Step 1 runs once, before any of this. After that, a pass is the same seven
actions every time.

  1. Sweep.                  -> 03-results.txt
  2. Link check.             -> 03-results.txt, closed postings cut
  3. LinkedIn.               -> 04-linkedin.txt
  4. Indeed.                 -> 04-indeed.txt
  5. Triage.                 -> 05-triage.txt, updated ledger.csv
  6. Decide every ranked row, Tier 1 first. Apply where it is worth it, set
     applied as you go, and get triage's advice for any role below Tier 1.
  7. Set every other row to skipped, or to closed where the posting was
     gone. For tier 3, the five-word reason is usually enough to decide.

The ledger stays in the root; everything else a pass writes goes into the run
folder, and triage attaches what the sweep and the LinkedIn and Indeed runs
wrote there.

When a full pass keeps not happening, shrink it rather than postpone it: the
sweep and its link check, then triage, is a real pass. The LinkedIn and Indeed
runs stack on top when there is time.

Prompt:
-------------------------------------------------------------------------------
Below these instructions is 03-results.txt, a table of job postings a
research run found, with its closing notes. A search index, a cached copy
or a job aggregator can hold a posting's full text long after the employer
closes it, so some of these rows may be for jobs that no longer exist. The
reverse happens too: an employer that moves to a new job board leaves its
old links dead while the role stays open. Check every row in this browser
before anything else reads the file.

For each row, open its URL in this browser and read what the page shows
once it has loaded. The row stays as it is if the page is a live posting
for that row's company and role on the company's own website or job board;

found, redirects to a job board or an error page, or says the job was

its careers link, and look for the same role there and on any job board
that page links to. If the role is listed, the row stays, with that
listing's URL in place of its own. If it is not, drop the row.

One exception: when the company is a staffing agency, a live posting on a
job board keeps the row as it is, since agencies often advertise nowhere
else.

mirrors keep closed postings listed, and do not judge fit: this check reads
only whether each posting is still open.

word of any row you kept.

The LINK CHECK block is always present. If no row was dropped or moved, it
is exactly this one line:

  LINK CHECK: NONE

Otherwise it is this header line, then one line per dropped or moved row,
and nothing else:

  LINK CHECK:
  CLOSED: [company] | [role title] | [what the page showed] | [URL]
  MOVED: [company] | [role title] | [new URL]

Name the file 03-results.txt. Plain text, no markdown. Give me the download

Prompt:
-------------------------------------------------------------------------------

1. Dedupe across all the attached result files. Match on company plus role
   title, normalized — not on URL. The same role reaches me as a LinkedIn or
   Indeed URL from one file and an ATS URL from another, and URL matching
   would file those as two separate roles. Where a role has two URLs, keep
   the one closest to the employer's own application page. Flag any that
   are staffing-agency reposts of the same underlying role.

   Normalized means case-folded, with dashes and slashes read as spaces,
   punctuation and repeated spaces collapsed, and any trailing location or
   remote suffix dropped — "Senior Web & Video Player Engineer - Remote" and
   "Senior Web & Video Player Engineer" are one role. Normalize the company
   half of the key the same way, dropping legal and decorative suffixes —
   Inc, Ltd, Corp, Studio: "Snap Inc." and "Snap" are one company.

   field keeps the posting's own title, minus any trailing location or
   remote suffix, which is what the ledger's existing rows already hold.

   stops the ledger matching, silently.

   anything already there with status applied, rejected or skipped goes in a
   short "already seen" list rather than the main ranking — unless the
   posting itself has materially changed: a new level, new location wording,
   or a substantively rewritten posting. A bare repost carrying only a fresh

   back into the ranking; rank it and say what changed.
   Anything already there at status new goes back into the ranking, marked
   as already in the ledger. Anything there at status closed goes back in
   too, marked reopened: I found that posting closed, so its turning up
   again means it was reposted. In every case, a posting already in the
   ledger under that key — at any status — never gets a second row:
   appending is only for postings not in the ledger at all, and the existing
   row stays untouched.

   If a row arrives with no token, work out which one it should carry from
   its location wording and say that you did. Restore UNVERIFIED to any row
   whose notes or Gap field says its URL is a mirror or that the posting
