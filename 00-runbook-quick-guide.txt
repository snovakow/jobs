WHY EIGHT RUNS

The first version of this step was one conversation covering all sixteen
keywords across both location passes. It burned most of a session's budget on
a quarter of the work and then stalled, holding rows it had never printed.

Browser work is far more expensive than chat, a stalled session cannot be
asked for its results, and LinkedIn will rate-limit a long run. Eight small
conversations bound all three. It is the same reasoning as ONE SEGMENT PER
RESEARCH RUN — the constraint there is search budget, here it is session
budget and site tolerance, and the fix is the same shape.

Each prompt tells the run to print its running table after every keyword.
That is deliberate and it is what makes the step recoverable: at any moment,
everything captured is already sitting in the conversation as text you can
copy out by hand. Do not ask a run to be tidier about this.


WHAT TO EXPECT

Expect this to still be the fiddliest part of the pass. It is a browser
driving a site that does not want to be driven, so a run may stall, lose its
place, or need nudging. That is normal.

The two passes have different ceilings and different date windows, and both
differences are deliberate.

A Toronto run should be cheap — four searches and at most ten postings
opened. That ten is a soft cap: on a Toronto-filtered search the card already
tells you what you need, so once the cap is reached the run keeps going and
captures from cards. It always finishes its four keywords. Because it is
cheap, it also runs a Past month window, matching the sweeps.

A remote run is the expensive one. Every posting gets opened, because that is
where US-only and US-work-authorization clauses hide and the card does not
show them. Its twenty is a hard stop, because there is no safe fallback — an
unopened posting on that pass is an unchecked posting.

Expect a remote run to stop on the count rather than on running out of
keywords. Twenty opens does not stretch to four keywords unless the set is
very narrow, so in practice a remote run covers its first keyword or two.
That is not a failure and it is not something to fix by raising the cap. It
is why the keywords are ordered narrowest first, and why the window stays at
Past week: the budget is going to decide your coverage either way, so it
should spend itself on the terms where you have the least competition and on
the freshest postings. Note which keywords it missed and either do a top-up
run or let them go.

Before you move a 04-* file into the run folder, glance down the title column
and ask whether these roles have anything to do with the keywords you just
ran. That is a five-second check and it is the only one that catches a run
capturing below the divider. The coverage list will not tell you — it reports
what the run believed it did. A set 1 file full of designers, consultants and
backend roles is not a thin market, it is a bad capture, and filing it puts
twenty junk rows in the ledger under that run's source code. That pollutes
the one measurement that tells you which keyword sets are earning their
place.

You do not have to do all eight in one sitting, or at all. Six runs and two
gaps is a normal pass. Attach whatever 04-* files exist.


IF A RUN STALLS

Ask for the partial table first, before you try to fix anything. Rows sitting
in the conversation are what you can lose; a stuck page is not. If the
composer is disabled, look for a stop control, then scroll the panel for an
approval prompt sitting below the fold, then check the site tab itself for a
modal or a challenge page.

Because each run prints as it goes, the fallback is cheap: select the last
printed table, paste it into a text editor, save it under that run's
filename. Step 4 only cares about the filename and that the URLs survived.

Note at the bottom of the file which keywords the run never reached. A thin
list reads very differently at triage depending on whether coverage was
complete or cut short.

If LinkedIn starts showing a challenge page, warning you about page volume,
or returning empty searches you can reproduce by hand in another tab, you
have been rate-limited. Retrying makes it worse. Save what you have and come
back to the remaining runs hours later, or drop them.


KEYWORD-EDITS.TXT

Everything about this file belongs here, even though the file itself is
attached to Step 1. Step 3 is where you find out a keyword is bad and Step 3
is where you fix it; Step 1 is only where the record gets read back.

It exists for one reason. A Step 1 re-run rebuilds all eight 02-linkedin-*
files from scratch and cannot see the keywords you replaced by hand, so it
reproduces the same bad term and you rediscover the problem a pass later.
Nothing else in the system reads this file. It is never attached to Steps 2,
3 or 4, and a pass never touches it.

WHEN TO WRITE A LINE. Only when you change a keyword in an 02-linkedin-* file
by hand. That is the entire trigger. Not for a thin run, not for a rate
limit, not for a stalled session, not for a keyword that found nothing.

WHAT MAKES A KEYWORD WORTH REPLACING. One thing only: it returns so many
close matches that capping at 25 hands you an arbitrary slice of an unrelated
market. You do not have to judge this yourself. A run that sees more than
about 100 close matches on a keyword prints a KEYWORD EDIT line after its
coverage list naming the term and the count. That line is the trigger, and it
is half of what you record.

Note that this threshold is higher than the 25-cap threshold, on purpose.
Thirty close matches means you captured 25 of 30 and the term is doing its
job. Six hundred means you captured 25 of 600 and the term has stopped
meaning anything.

WHAT IS NOT A REASON TO REPLACE A KEYWORD. Three things that look like
failures and are not:

  - No close matches. The term is narrow and working correctly. Nothing
    matching was posted in the window. This is the expected outcome for the
    narrowest terms and it is why they run first.
  - No divider appeared. LinkedIn ignored the term and ranked the general
    market instead. That is a ranking failure on their side, not a fault in
    the term. Replacing it costs you a good keyword and leaves the real
    problem in place.
  - A keyword ate a remote run's whole open budget. Expected — twenty opens
    rarely stretches to four keywords. It only means anything if the close-
    match count was also high, and then the count is what flags it.

WHAT TO WRITE. One line per change, appended to the root copy, in this form:

  set [n] [toronto|remote|both]: replaced "[old term]" with "[new term]",
  returned [count] close matches, [YYYY-MM-DD]

Both halves earn their place. The old term is what stops a re-run
reintroducing it. The count and date are what tell you later whether the
replacement held or whether that slot has been churning for a year.

Step 1's own rejections go in the same file, in the same form, with "step 1
rejection" where the count goes. Part B of Step 1 reports any candidate
keyword it rejected under the three keyword tests and what it used instead;
those are the same kind of fact — a term already ruled out — and they stop a
later re-run re-proposing it.

ONE DECISION THIS DOES NOT MAKE FOR YOU. A term that is too broad on the
remote pass may be fine on the Toronto pass, where the pool is far smaller
and the counts are much lower. Patching both keeps the pair's keyword lists
identical, which is what the Step 1 check list expects and what makes "set 1"
mean one thing. Patching only the offending file keeps a keyword that is
still working. Pick one and be consistent; the "both" option in the line
format above exists so the record reads the same either way.

===============================================================================
STEP 5 — APPLY
===============================================================================

Tier 1 only. Use the three lead bullets and the opening line the triage gave
you for each posting.

Apply within a few days of the triage. Anything found at day 25 of its life
has little runway left, and the ranking already accounts for that.

Set each one's status to applied in ledger.csv as you go, not later. If you
skip this, the next pass resurfaces the same roles and re-ranks them, and the
ledger becomes noise.

Roles you consciously pass on go to skipped. That keeps them out of future
rankings without pretending you applied. Tier 3 already arrives as skipped,
so the only rows you touch by hand are Tier 1 and Tier 2. Anything left at
new will correctly resurface next pass — that is the ledger working, not
failing.

Once or twice a year, sweep the ledger for rows still at new whose first_seen
is a couple of months old. Those are postings that closed without you
noticing. Set them to closed. Nothing breaks if you don't; they just make the
file harder to read.

You should never need to touch any of this. Step 1 copies these templates into
the 02-* files. They live here so Step 1 has something to copy, and so you can
rebuild an 02-* file by hand if you ever need to.

are placeholders Step 1 fills in.

Two rules for filling them in. Every word inside a template is verbatim; only
line breaks may move. And a bracket label changes the length of the line it
sits on, so once you drop one, close the paragraph up and rewrap it to 79
columns — a section header must never be left ending on a dangling dash.

SECOND MIGRATION — THE NO-DIVIDER RULE

The eight 02-linkedin-*.txt files need one more insertion, and this one
applies to the Toronto files as much as the remote ones. In each, find the

SWEEP PROMPT TEMPLATE (source text for Step 1 -> the four 02-segment files)

-------------------------------------------------------------------------------
Find live job postings that fit my background. Resume attached.

SEGMENT (this run only):
[segment description + target companies + keywords — filled in by Step 1]

EVERYTHING GOES IN THE TABLE. Location, recency and verification decide how a
posting is labelled, not whether I get to see it. There is no flagged
section, no eligibility-unclear section, no "worth your own look" paragraph
underneath. If you find yourself about to write a posting into prose because
it doesn't quite fit a rule, it belongs in the table with a status token. Only
the drop rules below remove a posting entirely.

STATUS TOKENS — the location column of every row begins with one of these, in
caps, then an em dash, then the posting's own location wording quoted rather
than paraphrased:

  OK          Meets the location rule below.
  RELOCATE    Strong match, wrong place.
  UNCLEAR     Remote, no stated country eligibility.
  STALE       Matches and still live, posted outside the 30-day window.
  UNVERIFIED  Corroborated across two or more independent sources, listing
              page could not be opened.

There is no sixth token. A row needing two carries both, space separated, in
the order listed above — "RELOCATE STALE".

LOCATION RULES — apply strictly to every posting, then label it.

OK if ONE of these holds:
(a) On-site or hybrid with the work location in Ontario, Canada — Toronto/GTA
    strongly preferred, also Mississauga, Markham, Waterloo-Kitchener,
    Hamilton, Ottawa, London.
(b) Remote, AND the posting explicitly states eligibility for candidates
    located in Canada. This includes "Remote — Canada", "Remote — North
    America", "Remote — US & Canada", or a named Canadian entity/EOR. Company
    HQ location is irrelevant; only stated candidate eligibility counts.

RELOCATE if the posting fails both of those on location alone and is a strong
match on the technical-depth test in the segment block above. I am willing to
relocate for the right opportunity, so these are worth seeing — which means
the bar is higher here than for an OK row, not lower. It has to be worth
moving for, not merely a role I could hold if I already lived there. An
ordinary match that happens to sit in another city is dropped, not tokened.
If you end up with more RELOCATE rows than OK rows, you have set the bar too
low; raise it and cut.

  "Remote — US only", postings requiring US work authorization, Remote —
  EMEA/LATAM/APAC and anything specifying a time zone that excludes Eastern
  Canada all land here when they are strong, and are dropped when they are
  not.

  Another Canadian city — Vancouver, Montreal, Calgary — is RELOCATE too,
  and the location column must say which city and country, so I can tell a
  domestic move from an international one at a glance.

  For anything outside Canada, put the posting's own words on work
  authorization and sponsorship in the location column: whether it sponsors,
  whether it requires existing authorization, or whether it says nothing. If
  it says nothing, write that. An empty field reads as "not checked".

UNCLEAR if the posting is remote and never states which countries it is open
to. Do not infer eligibility from the company's HQ.

Nothing is rejected for location alone. A posting is dropped only when it
fails the segment's technical-depth test, or fails verification below.
Location decides the token; it never decides the drop.

RECENCY: posted within the last 30 days. Record the posted date exactly as
shown. If no date is visible, write "undated" — do not estimate.

A posting outside the 30-day window that is still live on the employer's own
board gets the STALE token and keeps its real date. Do not drop it and do not
round the date to bring it inside the window. Still-posted-after-60-days is
information — it usually means the role is hard to fill, which is a reason to
show it to me rather than hide it. Drop it only if the posting is actually
gone.

VERIFICATION — this matters more than volume:
- Every posting must have a URL you actually opened and read.
- If a link 404s, redirects to a generic careers page, or the role is closed,
  drop it.
- Do not include any posting recalled from training data.
- Never construct or guess a job URL.
- Fewer verified, well-matched postings beats a long list. If you only find
  six real ones, return six.

There is exactly one exception. A posting you could not open, but which
appears on two or more independent sources with consistent company, title,
location and date, goes in the table with the UNVERIFIED token. Put the
source you actually read in the URL column, and say in the Gap field what you
could not confirm. This covers aggregators that block direct access to
individual listings. It does not cover a posting you inferred, remembered, or
saw once — those are still dropped, and a constructed URL is still never
acceptable.

WHERE TO LOOK: company career pages directly, and ATS-hosted boards
(Greenhouse, Lever, Ashby, Workable, BambooHR, SmartRecruiters, Workday). Also
try Wellfound, Welcome to the Jungle, Built In, and Canadian tech job boards.
Skip LinkedIn and Indeed — you can't read those postings, and I cover them
separately. Check the career pages of the specific companies listed in the
segment block above.

OUTPUT — plain text only, no markdown. One pipe-delimited table, one row per
posting, dashed rule under the header:
Company | Role title | Location + remote eligibility (status token, then the
posting's own wording) | Posted date | Comp if stated | Fit: one sentence
tying it to specific evidence in my resume | Gap: the single biggest thing
I'd be missing or the main risk | URL

One table, and only one. No second table and no sections after it holding
postings — the tokens do that work now.

Sort by fit, strongest first, as a single sequence. Do not group by token: a
strong RELOCATE belongs above a weak OK, and the token is what tells me the
difference.

Then, briefly:
- Any pattern you noticed in what this segment is actually asking for
- The kinds of adjacent role I'd likely have dismissed but shouldn't — the
  postings themselves stay in the table, described here only as a shape
- Where the search came up dry, and why

These closing notes describe patterns. If a specific posting is named in them
and does not also have a row above, the run has made the one mistake this
format exists to prevent.

THE FOUR SEGMENTS (source text for Step 1)

SEGMENT 1 — Graphics / XR
  Real-time 3D graphics, WebGL/WebGPU, Three.js, XR/VR/AR, spatial computing,
  game engine and rendering tooling, technical art tooling. Include creative/
  experiential studios and simulation companies.

SEGMENT 2 — Video infrastructure
